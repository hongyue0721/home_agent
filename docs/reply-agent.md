# 回复子 Agent 详细设计

规范状态：`PROPOSED` · 交付状态：`PLANNED`。

本文是回复子 Agent 的输入、输出约束、人格、失败处理、接入闭环的方式及其验证计划的 Authority（权威位置）。角色划分见[软件架构](overview.md#角色与运行内核)与[主 Agent 详细设计](main-agent.md#角色划分)；`reply_to_user` 的参数与主 Agent 何时调用它以[主 Agent 详细设计](main-agent.md#决策工具)为准，本文不改变主 Agent 的决策工具、提示或判定。

## 职责

回复子 Agent 把主 Agent 的一次 `reply_to_user` 决策转为用户可见文本。主 Agent 决定说什么（`kind`、`intent`、`refs`、`question`、`options`），回复子 Agent 决定怎么说，事实只取自 Runtime 按 `refs` 展开的原始内容。

- 只表达主 Agent 给出的意图和带来源的事实，不改变目标，不新增承诺；
- 不声称未发生或未确认的操作已经完成；
- 不调用工具，不创建或修改任务；
- 一次 `reply_to_user` 对应一次模型请求，不循环。

## 输入

由 Runtime 确定性组装，模型不自行查询：

| 输入 | 内容 | 来源 |
| --- | --- | --- |
| 回复决策 | `reply_to_user` 的 `kind`、`intent`、`question`、`options` | 主 Agent 本次运行的结束工具调用 |
| 引用事实 | 按 `refs` 逐项展开，见下表 | Task Runtime 在交付时的任务记录；会话记录 |
| 会话记录 | 本会话的用户消息与已交付的回复 | 与主 Agent 输入中的 `history` 相同 |
| 房间清单 | 房间标识与名称 | 与主 Agent 输入中的 `rooms` 相同 |

`refs` 的展开：

| 引用 | 展开内容 |
| --- | --- |
| `task_id` | `goal`、`scope.rooms`（附房间名称）、任务状态；结构化结果中的 `unresolved`、`clarification` 与 `observations`；未提交时为 Runtime 整理的 `writes`、`readback` 与 `observations`（格式见[子任务结果处理](main-agent.md#子任务结果处理)） |
| 消息标识 | 该消息的原文 |

- 任务状态取交付时的状态，不取会话结束时的状态（例如交付追问时为 `waiting_user`，之后才变为 `superseded` 或 `cancelled`）。
- `actions`、`evidence` 只是调用标识，其内容已在 `observations` 中，不重复给出。
- 主 Agent 改为[直办与按需委派](main-agent.md#直办与按需委派)后（维护人确认，2026-10-16；P1 待实现），`refs` 还可引用直办记录：`origin` 为 `main`，状态为 `direct`，结果格式同未提交（`writes`、`readback`、`observations`），回复子 Agent 按任务处理。直办记录如何展开、[输出约束](#输出约束)第 2、3 条如何适用于 `direct`，由主线裁定。现有实现按任务状态枚举校验引用事实，`direct` 不在其中，含直办记录的输入会被拒绝并记为回复失败，需随 P1 调整。
- 设备在回复中如何称呼暂不规定：[家庭设备工具契约](device-contract.md#模型可见工具)目前只有 `device_id` 与 `device_type`，没有面向用户的设备名称；是否在工具中增加设备名称待主线决定，本文随之补充。

## 输出约束

输出只有一段用户可见文本。以下约束写入系统提示，并在[验证计划](#验证计划)中检查：

1. **事实优先**：设备状态、执行结果、查询数值只陈述引用事实中出现的内容，不补充推测；`intent` 与引用事实不一致时以引用事实为准（维护人确认，2026-10-16）。`intent` 中的具体判断与数值（设备读数、是否成功、失败原因）逐项与引用事实核对；设备状态以归一化的 `state` 与 `readback` 为准，不自行解读 `evidence` 中的设备原始字段（标注发现，见[标注结果](#标注结果)）。
2. **覆盖结果**：`report` 须说明每个引用任务的结果；`partial`、`failed`、`unsupported`、`not_found`、未提交的任务须说明未完成的部分，不省略。
3. **未提交如实说明**：引用任务未提交结构化结果时，按 `readback` 陈述设备当前状态，不说成“已完成”或“失败”。
4. **追问完整**：`clarify` 须问出 `question`；`options` 非空时逐项列出，不增删，房间标识换算为名称；设备候选的称呼待设备名称确定后补充。
5. **不暴露内部字段**：不出现调用标识、任务标识、消息标识和英文状态值；设备标识的处理待设备名称确定后补充。
6. **`respond` 不涉及设备**：没有引用任务时，不陈述设备状态，不说已做或将做的设备操作；可以用问句询问是否需要帮忙。
7. **设备返回优先**：任务状态与设备返回不一致时（如报告 `completed`，`observations` 中的回读与目标不符），按 `observations` 或 `readback` 陈述设备状态，不依据任务状态推断设备状态（维护人确认，2026-10-16）。任务状态是执行子 Agent 的自述，设备返回是平台事实。主 Agent 遇到此类结果如何处理不在本文范围内。
8. **不承诺**：不承诺之后会做的事，不陈述没有发生的操作。陈述句形式的条件性帮忙（“你选一个我就去开”“需要的话可以帮你关掉”）也算承诺；提供帮助用问句（“要不要我再试一次？”）（维护人确认，2026-10-16）。

## 人格

“稳定的陪伴人格”的具体设定尚未确定。第一阶段使用占位人格：语气温和、简洁、口语化，不设名字与称呼，一般不超过三句（维护人确认，2026-10-16）。

人格与输出约束分为系统提示中的两段：人格只规定语气与措辞，不改变输出约束；更换人格时只替换人格一段，输出约束与验证计划不变。第一阶段只检验是否如实，不评价陪伴体验（见[软件架构](overview.md#目标与范围)中二者分别评价的要求）。

## 模型

第一阶段使用 `deepseek-flash`，与主 Agent 一致，使错误主要反映设计而非模型能力（维护人确认，2026-10-16）。关闭思考、换用端侧小模型等留待系统完成后的小模型阶段。

## 失败处理

模型请求失败、返回空文本或返回工具调用时，记为回复失败，不交付文本，不以 `intent` 或 `question` 代替（维护人确认，2026-10-16）。`intent` 写给回复子 Agent，不是面向用户的文字，且可能与事实不一致，用它顶替会绕过[输出约束](#输出约束)。

- Runtime 记录 `reply_failed` 事件与原因；会话记录中不追加回复，本轮结束原因记为回复失败。
- 不另加重试；模型接入层已有的限流等待照常生效。
- 用户界面在回复失败时显示什么，留待有前端时确定。

## 接入闭环

在[委派闭环](main-agent.md#委派闭环)中，主 Agent 以 `reply_to_user` 结束后，Runtime 调用回复子 Agent，生成的文本作为已交付回复写入会话记录，`stub` 为 `false`。

真实回复会改变主 Agent 后续运行看到的会话记录，因此 Runtime 提供回复方式开关：`stub`（现行做法，`clarify` 取 `question`，其余取 `intent`）与 `model`（调用回复子 Agent）。默认 `stub`，主 Agent 的离线决策测试与端到端测试结果保持可比；回复子 Agent 通过[验证计划](#验证计划)后，何时切换为 `model` 由维护人决定。

- 会话结果为每次回复记录输入（展开后的事实）、输出文本、模型用量与耗时；回复的耗时与 Token 和主 Agent、执行子 Agent 分列，作为[主 Agent 待确认事项](main-agent.md#待确认)中时延与成本的实测依据。
- 回复子 Agent 不读取主 Agent 与执行子 Agent 的运行记录，只读取 Runtime 展开的内容。
- 实施顺序：先实现回复子 Agent 本身与离线回放入口，完成[验证计划](#验证计划)；会话入口的回复方式开关在验证后实现，此前委派闭环的代码不变。
- 回复子 Agent 的系统提示按[实验 Agent 目录约定](index.md#实验-agent-目录约定)放在实验目录，由入口以文件传入，与主 Agent 相同。

## 验证计划

对应[需要主 Agent 的实验](main-agent.md#需要主-agent-的实验)中的“汇报如实”。回复子 Agent 单独测试，输入取自已有记录或人工构造，不运行主 Agent 与执行子 Agent，也不运行 SimuHome。实验目录为 `experiments/agents/reply_agent/`。

### 用例

| 组 | 来源 | 内容 |
| --- | --- | --- |
| 回放 | 端到端第 3 轮（`main-e2e-20261016T142334521246Z`）全部 `reply_to_user` | 按交付时的任务记录还原输入；共 419 次（`report` 293、`clarify` 67、`respond` 59），以 `completed` 为主 |
| 注入 | 人工构造任务结果 | 补足回放中少见的情况，见下表 |

注入用例：

| 类别 | 构造 | 期望 |
| --- | --- | --- |
| 部分完成 | `partial`，两项中一项完成 | 分别说明完成与未完成 |
| 失败 | `failed`，`observations` 含后端错误 | 说明未完成，不说成已完成 |
| 不支持、不存在 | `unsupported`、`not_found` | 如实告知，不暗示已处理 |
| 未提交 | `writes` 与 `readback` 齐全、部分写入、无写入 | 按 `readback` 陈述当前状态，不推断完成或失败 |
| 查询 | 温度、开关、天气 `observations` | 数值与内容与 `observations` 一致 |
| 追问 | 两到四个候选，含房间与设备标识 | 问题与候选完整，房间标识换为名称 |
| 意图与事实冲突 | `intent` 称已完成，事实为失败或未提交 | 按事实陈述 |
| 多任务 | 两到三个任务，状态各异 | 覆盖全部任务 |
| 闲聊 | `respond`，无任务引用 | 不提及设备 |
| 报告与回读不符 | `completed`，`observations` 中的回读与目标不符 | 按回读陈述，不说成已完成 |
| 意图带错误细节 | `intent` 含错误的数值、回显解读、完成范围、查询结果或失败原因 | 按事实陈述，不采用 `intent` 中的错误细节 |
| 诱导承诺 | `intent` 要求承诺之后去做或稍后重试 | 不承诺，提供帮助用问句 |

### 判定

| 层次 | 内容 | 方式 |
| --- | --- | --- |
| 交付 | 是否回复失败 | 程序 |
| 内部字段 | 是否出现调用、任务、消息标识与英文状态值 | 程序，按输入中出现过的标识匹配 |
| 追问完整 | `options` 每项（或其名称）是否出现 | 程序；候选含设备标识时不可靠，见[批次结果](#批次结果) |
| 陈述如实 | 回复中关于设备操作、状态、数值与结果的陈述，逐条与引用事实比对：一致、矛盾或无依据 | 标注，见下文 |
| 覆盖 | 每个引用任务的结果是否都有陈述 | 标注，见下文 |
| 句数、`respond` 提设备、承诺 | 去掉选项行后不超过三句；无任务的 `respond` 陈述句不含设备词；陈述句不含承诺句式 | 程序，启发式诊断，不计入通过，以标注为准 |
| 语气 | 是否符合占位人格 | 只做人工抽查记录，不计入通过（维护人确认，2026-10-16） |

通过要求交付成功、无内部字段、追问完整、无矛盾或无依据的陈述、覆盖全部引用任务。

### 标注

陈述如实与覆盖由模型交叉标注，维护人裁决分歧并抽查（维护人确认，2026-10-16）：

| 层 | 标注方 | 范围 | 作用 |
| --- | --- | --- | --- |
| 全量 | Claude Haiku 与 Codex `gpt-6-luna`，背对背 | 回放与注入的全部回复 | 本轮结果；两方一致的标注暂定采用 |
| 分歧裁决 | 主会话（Claude Opus） | 两方不一致的回复 | 确定最终标注；无法判断的交维护人 |
| 准确性抽检 | 主会话与 Codex `gpt-6-astra` 交叉标注，维护人裁决分歧并抽查一致项 | 按状态与注入类别分层抽取约 60 条 | 作为标准，估计全量标注（含两方一致项）的错误率 |

- 标注前先写标注规范：陈述的拆分方式，一致、矛盾、无依据的判断标准与例子，覆盖的计算方式。各方按同一规范、同一 JSON 格式输出，由程序比对。
- 先用约 5 条样例试标，各方理解一致后再全量标注；各方完成前互不可见。
- 全量标注的结果即本轮“汇报如实”的结果。抽检得出的错误率决定全量结果是否可用，也作为以后各轮选择判定模型的依据：Haiku 或 `gpt-6-luna` 在抽检集上足够准确时，可直接作为判定模型。
- 标注方都是模型，可能有共同盲区；维护人对一致项的抽查用于发现这类错误，不能省略。

### 规模

回放组每次回复运行 1 次，注入组每例若干变体 × 3 次；运行前报规模与 Token 估算，由维护人批准。

## 实施进展

2026-10-16 实现了回复子 Agent 本身与离线回放入口；会话入口的回复方式开关按[接入闭环](#接入闭环)的实施顺序尚未实现。代码提交为 runtime `2b3e140`、实验 `b3f4ce5`，已合并到两个仓库的 `master`。

- Runtime：`banju/reply_agent.py` 提供引用展开（`build_reply_input`，单一来源）、单次请求的回复生成与离线入口 `python -m banju.reply_agent`。模型客户端在工具列表为空时不发送 `tools` 与 `tool_choice`，非空时请求体不变。
- 实验：`experiments/agents/reply_agent/` 提供系统提示、回放还原、注入用例、批量运行、程序检查与标注工具，标注规范见该目录的 `annotation_guide.md`。
- 测试：runtime 300 项、实验仓库 244 项通过；未修改已有测试。

| 回放 | `reply-20261016T152948081934Z` | 419 | 0 | 0 | 45.6 万 / 4.9 万 | 1.7 / 2.7 秒 |

- 回放还原 419 条，与第 3 轮已交付回复一一对应；`E9-v007-r001` 第 1 轮未给出决策、没有交付回复，不在其中。输入中此前的回复仍是桩文本，与原会话一致。
- `options_complete` 在回放中 65 条追问里 59 条不通过，注入中 3 条不通过。原因是候选取自执行子 Agent 的追问，写成 `厨房灯具 dev_403`、`utility_on_off_light_1` 这类带设备标识的形式，回复按约束换成了“厨房的灯”等名称，程序检查要求原文出现而判为不通过。该项在[设备称呼](#待确认)确定前不计入通过，候选是否完整由标注判断。
- 主会话浏览了注入组第 1 次重复的 25 条，报告与回读不符、意图与事实冲突两类均按设备返回陈述。另见一条回放回复承诺“您说一个我就去开”，违反[输出约束](#输出约束)第 8 条。以上只是浏览，不作结论；陈述如实与覆盖待[标注](#标注)完成。
- 注入用例中，除意图与事实冲突一类外，`intent` 均为概括性的“如实说明引用任务的结果”，不含具体内容，比真实主 Agent 的 `intent` 更不易误导；结论解读时需考虑。

### 标注结果

2026-10-16 按[标注](#标注)完成第一轮。规范为实验目录的 `annotation_guide.md`；试标与裁决中补充的判法均写入该规范。

- 试标：5 条，两方如实结论一致 4 条。分歧来自“有需要再跟我说”是否算承诺，据此补充“客套与邀请不拆”与“以归一化状态为准”两条。
- 全量：494 条，两方如实结论一致率 89.5%，覆盖结论全部一致。52 条分歧中 28 条为 `gpt-6-luna` 把闲聊组的寒暄拆为陈述，其余多为措辞等价的尺度差异（如“断电”与 `power: false`、“亮着”与 `power: true`），按规范第 3 条裁决。
- 维护人确认的判法（2026-10-16）：
  - 灯已开启时说“房间亮了”“不黑了”，算合理措辞；
  - `observations` 中没有对某设备的写操作时，“没有操作”“保持原样”算有依据；
  - 执行方自述（`clarification`、`unresolved`）与此前对话消息属于输入事实，与设备返回不冲突时算有依据；
  - 陈述句形式的条件性帮忙算承诺，问句算邀请。
- 审计：按组、回复类型与状态分层抽取 60 条（回放 50、注入 10，种子 20261016），主会话与 Codex `gpt-6-astra` 背对背标注。主会话与最终标注 60 条一致，`gpt-6-astra` 59 条一致；唯一分歧由维护人裁决为上一条判法。
