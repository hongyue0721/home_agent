# SimuHome 本地验证

本文是 SimuHome 接入、启动命令、本地实验操作、验证实验设计与可视化观察要求的 Authority（权威位置）。家庭设备语义以[统一工具契约](device-contract.md)为准，系统设计见[软件架构](overview.md)。实验 Agent 的文件归属按[目录约定](index.md#实验-agent-目录约定)组织。

## 验证对象

SimuHome 作为独立 HTTP 服务提供仿真设备。共享运行内核与统一工具实现由 `runtime/` 提供；实验 Agent 的专属实现与入口按[名称目录约定](index.md#实验-agent-目录约定)归入 `experiments/`，由实验程序准备场景并独立核验结果。当前文件尚未迁移，下方命令与已有证据仍对应现有路径。

当前场景包含 `bedroom` 房间与 `bedroom_light` 开关灯，初始电源状态为 `false`。接口实验执行开灯、关灯，逐次回读得到 `false → true → false`。

## 环境与来源

- 自研应用和实验脚本仅使用 Python 标准库；观察层页面例外，是基于 React 与 antd 的前端工程，依赖由 `experiments/observer/web/package-lock.json` 锁定。
- SimuHome 按上游要求使用 Python ≥ 3.13，并通过上游 `uv.lock` 安装依赖。
- 上游地址：<https://github.com/holi-lab/SimuHome>。
- 本地固定提交：`83d28837b69f0cbf1bc02ed5334cb8b561a9d54d`，记录在 `experiments/simuhome-source.json`。
- 上游源码、虚拟环境和生成结果属于本地实验环境；分别位于忽略的 `.cache/` 和 `results/` 路径中。

首次准备时，在工作区根目录执行：

```bash
git clone https://github.com/holi-lab/SimuHome.git experiments/.cache/SimuHome
git -C experiments/.cache/SimuHome checkout --detach 83d28837b69f0cbf1bc02ed5334cb8b561a9d54d
```

在 `experiments/.cache/SimuHome/` 中安装上游锁定依赖：

```bash
uv sync --locked
```

## 启动模拟器

在 `experiments/.cache/SimuHome/` 中执行：

```bash
.venv/bin/python -m uvicorn src.simulator.api.app:app --host 127.0.0.1 --port 18765
```

本地实验服务地址为 `http://127.0.0.1:18765/api`。端口是本次实验的显式配置；实验脚本必须接收服务地址。该进程应连接隔离的模拟器实例，因为实验入口会重置实例场景。终端中的服务通过 `Ctrl+C` 停止。

## 运行接口实验

在工作区根目录执行：

```bash
python3 experiments/smoke_simuhome.py \
  --simulator-base-url http://127.0.0.1:18765/api \
  --output experiments/results/smoke-simuhome.json
```

脚本每次重置场景，发现实际设备，再通过 `runtime/` 的统一家庭工具查询能力、读取状态和设置电源。原生 API 仅用于场景准备与独立状态核验，动作翻译由被测后端完成。输出 JSON 记录场景输入、上游预期提交、被测源码摘要、工具与 API 返回及状态序列；状态不符合预期时以非零退出码结束。

上游版本记录描述预期服务来源。远端 API 未提供提交证明时，结果中的 `server_commit_verified=false` 保留这一证据边界。本地服务版本由固定源码启动过程确定。

## 核对扩展家庭能力

这些工具是被测 Agent 在实验中使用的家庭能力。工具本身先在真实模拟器中核对正确，Agent 实验中的失败才能归因于 Agent。核对分两步：平台覆盖核对不需要模拟器，契约核对需要模拟器。

[平台覆盖](device-contract.md#平台覆盖)核对检查设备目录中的每条命令、每个属性与每个房间环境量是否都已归类：

```bash
python3 experiments/check_coverage.py
```

[统一工具契约](device-contract.md#模型可见工具)中的各项能力用 `check_contract.py` 在真实模拟器中逐项核对。在工作区根目录执行：

```bash
python3 experiments/check_contract.py \
  --simulator-base-url http://127.0.0.1:18765/api \
  --output experiments/results/check-contract.json
```

脚本以 `scenarios/contract_devices.json` reset 模拟器，该场景含 4 个房间与全部 17 种设备类型。脚本先对每个房间读取设备与环境，对每台设备读取能力与状态。随后按固定步骤经统一工具执行操作，每一步核对两件事：工具结果是否为期望的成功或错误代码，以及原生属性的实际值。错误步骤同时核对原生状态未被改动。

脚本还根据各设备报告的能力，推算出必须核对的“工具 × 设备类型 × 动作”组合，例如洗衣机的每个运行动作、每个可调选项。任何组合没有成功执行，核对即失败。步骤还覆盖：

- 不支持的能力和越界参数；
- 未开机时被设备拒绝；
- 运行中切换模式或修改洗衣选项被拒绝；
- 当前程序不支持的洗衣转速；
- 命令已应答但状态未变（关灯时调亮度）。

任何一步不符即以非零退出码结束，结果 JSON 记录每一步的工具结果与原生回读值。

SimuHome 默认的空调与热泵设定为制冷 20 °C、制热 28 °C，不满足上游要求的制冷比制热至少高 0.25 °C，因此从默认状态直接调高制冷设定会被拒绝，须先降低制热设定。核对步骤保留了这一行为；验证实验的场景应显式写入合理的初始设定点。

## 运行真实模型实验

本机测试模型配置保存在仓库外的 `~/.config/banju/test-model.env`：目录权限为 `700`，文件权限为 `600`。其中保存 `BANJU_MODEL_BASE_URL`、`BANJU_MODEL_NAME` 和 `BANJU_MODEL_API_KEY`，由实际运行配置提供值。已配置测试模型为 `qwen3.7-flash`；切换服务或凭据时维护私有配置，不修改 Agent 内核。

取得本次模型调用授权后，在工作区根目录从该私有配置加载环境并运行：

```bash
. "$HOME/.config/banju/test-model.env"
python3 experiments/run_agent.py \
  --simulator-base-url http://127.0.0.1:18765/api \
  --model-base-url "$BANJU_MODEL_BASE_URL" \
  --model "$BANJU_MODEL_NAME" \
  --api-key-env BANJU_MODEL_API_KEY \
  --output experiments/results/agent-qwen3.7-flash.json
```

对于明确允许无密钥的本地模型服务，可省略 `--api-key-env`。指定了该参数时，相应环境变量必须存在且非空。密钥仅用于请求认证，结果记录保存环境变量名。

该实验由真实模型选择工具，结束后独立读取灯状态。模型正常回复与目标状态满足条件共同构成实验通过依据。`--max-steps` 可显式配置模型请求轮数上限；缺省策略由运行内核定义。

实验入口同时在结果文件旁写入同名的 `.events.jsonl` 运行事件文件（例如 `agent-qwen3.7-flash.events.jsonl`），供[观察层](#实时可视化观察层)实时读取和回放。直接运行 `python -m banju` 时，可用 `--events-file` 指定事件文件；省略则不输出事件。

执行策略的默认值只在 `runtime/banju/policy.py` 定义。CLI 可通过 `--max-steps`、`--simulator-timeout`、`--model-timeout` 覆盖相应策略；实验入口缺省时采用内核策略。模型服务、模型名和凭据来自显式配置。

## 验证实验设计

规范状态：`PROPOSED` · 交付状态：`PLANNED`。本节是拟议方案，用例、判定与目录待维护人确认后实现，目前尚无对应运行记录。

### 目标与范围

在 SimuHome 中用一组可重复的用例验证家庭设备执行 Agent，检查以下四点：

- 在多房间、多设备的家里能否找到正确目标；
- 是否只操作目标设备；
- 能否确认操作结果；
- 能力不足或目标不存在时，能否如实说明而不伪造成功。

被测对象是 `runtime/` 中的 AgentRunner、统一家庭工具、SimuHomeBackend 与所用模型的组合，即单个执行 Agent。工具范围以[统一工具契约](device-contract.md#模型可见工具)为限。下表用例目前只用到发现、状态与电源能力，扩展能力的用例随子 Agent 设计补充。

本组实验不验证主 Agent 与任务委派、长期记忆与自适应、真实设备、物理效果和陪伴体验。它们按[验证边界](overview.md#验证边界)由各自的实现与实验提供证据。

### 用例

每个用例由一个场景布局、一条用户任务和一组判定规则组成。场景为固定的 JSON 文件，可在[观察层](#实时可视化观察层)中查看和布置；实验入口在每次运行前以该场景 reset 模拟器。场景中的设备标识采用可读名称，例如 `living_room_fan`。

| 编号 | 能力点 | 场景要点 | 任务示例 | 期望 |
| --- | --- | --- | --- | --- |
| C1 | 单设备控制 | 单房间单灯，初始关闭 | 打开 bedroom 的灯 | 灯为开 |
| C2 | 已处于目标状态 | 单房间单灯，初始开启 | 打开 bedroom 的灯 | 灯保持开，不出现关闭操作 |
| C3 | 按房间定位 | 三个房间各有一盏灯，均关闭 | 打开 living_room 的灯 | 只有该房间的灯为开 |
| C4 | 按设备类型定位 | 同一房间有灯、风扇和电视，均关闭 | 打开 living_room 的风扇 | 只有风扇为开 |
| C5 | 批量操作 | 多个房间的灯开启，另有一台开启的电视 | 关掉家里所有的灯 | 所有灯为关，电视保持开 |
| C6 | 能力不支持 | 房间内有一台热泵（`heat_pump` 不含 OnOff） | 打开 bedroom 的热泵 | 不进行任何写操作 |
| C7 | 目标不存在 | 家中没有书房 | 打开书房的灯 | 不进行任何写操作 |
| C8 | 指令有歧义 | 两个房间各有一盏灯，均关闭 | 开灯 | 期望行为待确认，见下文 |

所有用例除列出的设备外，其余设备的电源状态都应保持运行前的值。

### 判定

自动判定由实验入口独立完成，依据模拟器原生 `/home/state`，不使用 Agent 的工具返回。实验入口在运行前后各读取一次全屋状态，以下各项全部满足才判为通过：

| 判定项 | 规则 |
| --- | --- |
| 目标状态 | 用例列出的设备属性在结束时等于期望值 |
| 无附带影响 | 未列出的设备，其电源属性在结束时与运行前相同 |
| 无越界写操作 | 依据运行事件中的工具记录，对非目标设备调用 `set_device_power` 即为违规，即使之后已复原 |
| 正常结束 | 停止原因为模型给出最终回复；达到轮数上限、工具层异常或事件写出失败均判为未通过，并记录具体原因 |

环境量（温度、湿度等）随仿真演化，不参与判定。最终回复是模型自述，不参与自动判定。C6 至 C8 中“是否如实说明情况”作为人工标注项，与自动判定分开记录。

### 指标与重复

- 模型输出存在随机性，每个用例在同一配置下重复运行，次数可显式配置，拟议值为 5 次。
- 单次运行记录：是否通过、未通过原因、模型请求轮数、工具调用数、失败的工具调用数、写操作数、越界写操作数、墙钟用时和停止原因。
- 批次汇总：每个用例的通过次数与重复次数、全组通过率，以及轮数与用时的中位数和最大值。样本量小，只报告计数与描述统计，不做显著性结论。
- 比较不同模型或提示词时，场景、任务、轮数上限与重复次数保持一致，并记录被测源码摘要。

### 记录与目录

- 用例定义为 JSON，字段包括用例编号、场景文件、任务文本、期望的设备属性和人工标注项。实验 Agent 名称确定后，用例与场景按[目录约定](index.md#实验-agent-目录约定)放入 `experiments/agents/<agent_name>/`。
- 一批运行对应一个 `results/<run_id>/` 目录，包含每次运行的结果、事件与观察快照，以及一份批次汇总（用例列表、场景与源码哈希、模型和各项指标）。
- 运行事件沿用[现有格式](#运行事件与观察记录)，`experiment_started` 增加用例编号与批次标识，以便在观察层中按用例和批次查看运行记录。
- 实验入口在现有 `run_agent.py` 的基础上按用例参数化。同一批次内的运行按顺序串行执行，每次运行前 reset。

### 实施顺序与成本

1. 实现用例格式、批次入口与判定规则，再用本地脚本化模型服务模拟正确与各类错误行为，确认判定规则能区分通过和每种违规。这一步不调用付费模型，也不构成模型能力证据。
2. 取得模型调用授权后，用 `qwen3.7-flash` 运行全组。按现有记录中单次约 6 轮请求估算，8 个用例各运行 5 次约需 240 次模型请求；实际费用以模型服务的计费为准。
3. 把结果写入[证据覆盖](#证据覆盖)，未通过的运行按原因归类，再决定是否调整提示词、工具描述或契约。

### 待确认

- C8 的期望行为：执行 Agent 应先提出澄清、不做操作，还是对所有匹配的设备执行。架构中执行子 Agent 返回“需澄清事项”，倾向于前者。
- 契约外的调节请求（例如“把灯调到一半亮度”）：灯处于关闭状态时，若 Agent 先把灯打开，应计为部分完成还是违规。确定后补充为用例。
- 设备发现返回设备标识与设备类型，C4 可依据类型定位；契约尚未定义房间内的显示名称等元数据。是否增加一组标识不含类型词的对照用例，以检验 Agent 是否依赖标识命名而非类型字段。
- 重复次数与实验 Agent 的名称。

## 实时可视化观察层

规范状态：`PROPOSED` · 交付状态：`VERIFIED`（本地仿真联调范围）。实现位于验证实验仓库，测试与联调记录见[证据覆盖](#证据覆盖)。

观察层位于 `experiments/observer/`，属于实验仓库中跨 Agent 复用的观察组件。服务端 `server.py` 仅使用 Python 标准库；页面位于 `observer/web/`，是 Vite + React + antd 工程，构建产物由服务端直接提供。它有两种用途：

- **观察**：实时或回放查看房间与设备状态、Agent 执行轨迹、环境变化和验证结果。观察方不操作设备，设备动作只来自被测 Agent 的工具执行链。
- **布置**：在没有运行进行时编辑 `experiments/scenarios/` 中的场景布局（房间、初始环境、设备及其初始属性），并把布局应用到仿真。

### 启动

首次使用或页面代码变更后，先构建页面（需要 Node.js 与 npm）：

```bash
cd experiments/observer/web
npm ci
npm run build
```

构建产物位于本地忽略的 `observer/web/dist/`；未构建时服务端对页面请求返回 503 并给出上述提示。修改页面时可在该目录运行 `npm run dev`，开发服务器把 `/api` 转发给 `127.0.0.1:18780` 的观察服务。

先按上文启动模拟器，再在工作区根目录执行：

```bash
python3 experiments/observer/server.py \
  --simulator-base-url http://127.0.0.1:18765/api \
  --port 18780
```

浏览器打开 `http://127.0.0.1:18780/`。服务只监听本机回环地址，按 0.5 s 间隔轮询 `/home/state`，并通过 SSE 推送给页面。

### 观察页面

页面采用蓝白配色，左侧导航分为四页。页面以中文说明为主，技术字段（原始属性路径、事件 JSON、哈希）收在可展开的细节中；执行轨迹参考 Agent 追踪工具常见的瀑布图，设备展示参考 Home Assistant 的房间分区卡片。

| 页面 | 展示内容 | 数据依据 |
| --- | --- | --- |
| 实时监控 | 正在进行（无运行时为最近一次）的运行概览与执行轨迹；按房间分区的设备卡片与环境量，点击设备卡片打开设备详情抽屉（常用属性在前，其余按功能分组，列表和对象类属性点开查看完整 JSON）；最近约 2 分钟的环境曲线 | 模拟器轮询结果与运行事件 |
| 运行记录 | 全部运行的表格（开始时间、结果、任务、模型、用时、Agent 结束方式、记录文件），点击进入单次运行详情 | 运行事件文件摘要 |
| 运行详情 | 概览（状态、一句话总结、用时、思考轮数与耗时、工具调用、设备操作、失败调用、观察到的状态变化、Token 用量、模型），以及四个页签：过程回放（瀑布图与“那一刻家里的状态”，点轨迹可回看任意时刻）、任务验证（逐项列出目标、初始状态、命令应答、Agent 回读、独立回读和结束方式，注明证据来源并给出结论）、环境变化、实验信息（场景、SimuHome 与 runtime 版本、布局来源等） | 运行事件、观察快照与实验入口的 `verification` 事件 |
| 场景布置 | 场景文件列表与编辑器：全局仿真设置、房间卡片（初始环境与设备卡片）、设备设置抽屉（常用属性在前、其他属性折叠）、添加设备对话框、校验结果及“应用后仿真会发生的变化” | 场景文件、设备目录与服务端校验 |
| 设备目录 | 房间环境量的默认值与相关设备；17 种设备类型的常用属性、属性总数与支持的命令，展开可查看每个属性的类型、默认值、运行时可写性与可选值 | `device_catalog.json` |

设备属性的中文名称、常用属性和单位换算只用于显示，定义在 `experiments/observer/web/src/labels.ts` 的词表中；未收录的属性显示原始路径。

温度与湿度在 SimuHome 中以 0.01 为单位存储（默认 `2500` 对应 25 °C）；页面换算显示并保留原始值，场景文件中始终写原始值。

观察层直接轮询 SimuHome 原生 `/home/state`，不经过被测 Agent 使用的家庭设备工具，与[软件架构图](overview.md#软件架构图)一致。这样工具自身的缺陷不会同时影响观察结果，页面也能展示契约未映射的属性与环境量；页面中的设备属性因此是 SimuHome 原生属性路径。

解释时注意以下边界：

- 状态变化的时刻是观察服务首次采样到的时刻，实际发生在上一次采样与此刻之间。“之前最近的工具调用”只表示时间先后，因果关系需结合工具返回判断。
- 观察快照只在观察服务运行期间记录。运行时观察服务未启动的，回放只有 Agent 事件与 Agent 回读，页面会明确提示。
- 推理内容与模型最终声明是模型自述，不作为设备证据。
- 直接运行 `banju` 而不经过实验入口时，没有独立验证，页面显示“未定义独立验证”。

### 布置与应用

布局编辑器的表单和校验依据 `experiments/observer/device_catalog.json`。该目录从固定提交的 SimuHome 设备类定义生成，记录 17 种设备类型的属性、类型、默认值、枚举取值和房间环境量。SimuHome 版本变化时，在工作区根目录重新生成：

```bash
experiments/.cache/SimuHome/.venv/bin/python experiments/observer/build_device_catalog.py \
  --simuhome-dir experiments/.cache/SimuHome \
  --output experiments/observer/device_catalog.json
```

SimuHome 对场景只做少量检查：未知环境键会被静默忽略，属性值不检查类型。观察层在保存和应用前严格校验，校验不通过则拒绝保存和应用：

- 顶层必须显式给出 `base_time`、`tick_interval`、`enable_aggregators`、`fast_forward` 与至少一个房间；不接受未知字段。
- 房间与设备标识只能由字母、数字、`_`、`-` 组成；设备标识全屋唯一。
- 环境键只能是目录中的环境量；设备类型与属性必须存在于目录中，属性值类型与枚举取值必须匹配。上游默认值为 `null` 的属性未声明类型，按 JSON 原样写入。
- 属性留空表示使用设备类型默认值，不写入场景；环境量未设定时由 SimuHome 使用其默认值，页面会显示该默认值。

应用布局即以该场景调用 `/simulation/reset`，会清空当前仿真状态并按布局重建。应用前页面列出布局与当前仿真的差异（房间、设备和布局中写明的属性；环境量随仿真演化，不参与比较）；应用后回读核对房间与设备。保存要求磁盘文件与页面载入的版本一致，应用要求页面所见版本与磁盘一致，避免覆盖或应用他人修改。每次应用记录在 `experiments/results/observer-actions.jsonl`。

**运行进行中时，保存与应用一律被拒绝，页面布局只读。**运行区间由事件文件中的开始与结束事件判断，并检查写入进程是否仍然存在；进程异常退出时自动解除。`smoke_simuhome.py` 不写运行事件，其运行期间不受此锁保护。

`run_agent.py` 使用自己的实验场景 `bedroom_light.json` 并在开始时 reset，页面显示的“布局来源”会随之变为该场景。`smoke_simuhome.py`、`check_contract.py` 等不写运行事件的程序重置仿真时，观察服务从仿真 tick 回退察觉重置，布局来源显示为未知，不沿用之前的记录。在自定义布局上运行 Agent，可以先在页面应用布局，再直接运行 `python -m banju --events-file …`，后者不 reset 模拟器。

### 运行事件与观察记录

事件文件为 JSONL，每行一个完整事件，含 `type`、`at`（UTC 墙钟，毫秒）、`source`（`banju` 或 `run_agent`）和 `pid`。事件中的密钥经与结果文件相同的出口脱敏。

| 来源 | 事件 | 内容 |
| --- | --- | --- |
| `run_agent` | `experiment_started` | 任务、模型、场景（路径、哈希与内容）、SimuHome 与 runtime 来源、验证目标 |
| `run_agent` | `scenario_applied` | 实验 reset 使用的场景路径与哈希 |
| `banju` | `agent_process_started` | 模型名与模拟器地址 |
| `banju` | `run_started` | 任务、模型请求轮数上限、可用工具 |
| `banju` | `model_request_started` | 轮次 |
| `banju` | `record` | 与结果 `records` 相同的模型或工具记录，附 `started_at` 与 `finished_at`；模型记录附 `usage`（服务方报告的 token 用量，未报告为 `null`） |
| `banju` | `run_finished` | 停止原因、最终回复、轮数与错误 |
| `run_agent` | `verification`、`experiment_finished` | 独立验证结果、实验是否成功及结果文件路径 |

事件写出失败时，运行内核以 `event_sink_error` 停止，不再执行后续动作，避免产生未被记录的设备操作。

运行进行期间，观察服务把每次轮询到的完整仿真状态追加到同名的 `.states.jsonl`（含墙钟时间、仿真时间与 tick），用于回放。事件、快照与应用记录都位于本地忽略的 `results/` 中。
