# 主 Agent 详细设计

规范状态：`PROPOSED` · 交付状态：`PLANNED`。

本文是主 Agent 的职责边界、第一阶段范围、决策与委派、子任务结果处理、交给回复子 Agent 的内容及主 Agent 验证计划的 Authority（权威位置）。它细化[软件架构](overview.md)中的[角色与运行内核](overview.md#角色与运行内核)和[委派与反馈](overview.md#委派与反馈)。执行子 Agent 的任务格式与结构化结果以[执行子 Agent 详细设计](executor-agent.md)为准，本文只说明主 Agent 如何产生任务与使用结果。

## 角色划分

主 Agent 只负责决策，不直接生成用户可见回复；用户可见回复由回复子 Agent 生成（维护人确认，2026-10-15）。三种角色复用同一 AgentRunner，运行上下文与工具范围相互独立。

| 维度 | 主 Agent | 回复子 Agent | 执行子 Agent |
| --- | --- | --- | --- |
| 职责 | 理解用户意图，决定回应、委派、追问或汇报 | 依据主 Agent 的决定与已有事实组织用户可见回复 | 查询环境、选择工具、编排动作、验证局部目标 |
| 输入 | 用户原话、本会话记录、任务状态与子任务结果 | 主 Agent 给出的回复意图与事实、本会话记录 | 任务目标、范围、约束与最小背景 |
| 工具 | 任务委派与管理 | 无设备工具 | 当前任务范围内的设备与外部工具 |
| 输出 | 结构化决策 | 用户可见文本 | [结构化结果](executor-agent.md#结构化结果) |
| 人格 | 不承载表达人格 | 稳定的陪伴人格 | 中性执行角色 |

回复子 Agent 的约束：

- 只表达主 Agent 给出的意图和带来源的事实，不改变目标，不新增承诺；
- 不声称未发生或未确认的操作已经完成；
- 不调用设备工具，不创建任务。

## 第一阶段范围

第一阶段只建立委派闭环：

1. 收到用户消息，判断是否需要执行；
2. 需要执行时构造执行任务并委派；
3. 收到执行子 Agent 的结果，决定汇报、追问或继续委派；
4. 用户补充或修改要求后，恢复或修改原任务；
5. 需要对用户说话时，把回复意图与事实交给回复子 Agent。

第一阶段不包括：

- **长期记忆**：经历记忆、偏好与用户信息、有效约束与持续委托均不实现。记忆作为后期研究主题，第一阶段的主 Agent 作为其对照基线（维护人确认，2026-10-15）。会话记录、任务状态和实时设备状态仍属于第一阶段。
- **定时与环境事件**：此类事件需要持续委托，第一阶段输入只有用户消息与子任务结果。
- **任务进行中的修改与取消**：需要 Runtime 在执行期间接收新消息，作为后续阶段，其实验见[验证计划](#验证计划)。

请求依赖用户偏好（例如“调到我平时喜欢的温度”）时，第一阶段没有可用的偏好记录，主 Agent 须追问，不以默认值代替。

## 决策

每次输入后，主 Agent 给出一项结构化决策：

| 决策 | 含义 |
| --- | --- |
| 回应 | 不需要执行，交回复子 Agent 回应，例如闲聊或解释 |
| 委派 | 创建执行任务，字段见[任务输入](executor-agent.md#任务输入) |
| 追问 | 需要用户补充信息，包括转达执行子 Agent 的澄清问题 |
| 汇报 | 子任务结束后，把结果交回复子 Agent 告知用户 |

决策的具体字段、一次输入能否产生多项决策（例如委派多个任务，或委派同时告知用户“正在处理”）尚未确定。

委派时，`goal` 用自然语言写出目标，`context` 只放完成任务所需的最小背景，不复制完整会话。`scope` 中哪些字段必须由主 Agent 给出，取决于[范围写错实验](#验证计划)的结果：若 `discovered` 等暴露策略不依赖 `scope.capabilities` 仍能保持效果，主 Agent 只需给出房间、设备类型与领域。

## 子任务结果处理

执行子 Agent 的结果中，“做了什么”（`actions`）与“证据”（`evidence`）改由 Runtime 依据运行记录填写，模型只提交状态、未完成事项与澄清问题（维护人确认，2026-10-15，尚未实现，见[结构化结果](executor-agent.md#结构化结果)）。

主 Agent 按状态处理：

| `status` | 主 Agent 的处理 |
| --- | --- |
| `completed` | 汇报 |
| `partial` | 汇报已完成与未完成的部分 |
| `failed` | 决定重试、换用其他方式或告知用户；策略由[验证计划](#验证计划)中的失败处理实验确定，不允许无限重派 |
| `needs_clarification` | 追问用户，用户回答后续派 |
| `unsupported`、`not_found` | 告知用户 |

执行子 Agent 未提交结构化结果时，主 Agent 不直接读取运行记录（维护人确认，2026-10-15）。拟议由 Runtime 确定性地整理一份结果：

- 标明“未提交，由系统按运行记录整理”，状态记为未提交，不推断为完成或失败；
- 列出运行记录中实际执行的写操作；
- 回读这些操作涉及设备的当前状态，附在结果中。

该整理不是代为提交的结构化结果，执行子 Agent 的结果仍记为未提交（见[结构化结果](executor-agent.md#结构化结果)）。主 Agent 据此如实告知用户或决定续派。维护人曾提议由轻量子代理读取运行记录；运行记录本身是结构化数据，确定性整理不需要模型，也不会代为推断结论。两种方式的取舍待确认。

## 验证计划

各实验尚未运行。判定优先使用平台原生状态、运行记录和结构化决策等可自动核对的事实。

### 范围写错

不依赖主 Agent 实现，用现有执行子 Agent 进行：故意改动任务 `scope`，比较各暴露策略的承受能力，为主 Agent 应输出的范围字段提供依据。

| 写法 | 以“打开客房的灯”为例 | 期望 |
| --- | --- | --- |
| S0 正确 | 客房、灯、`power` | 只打开客房的灯 |
| S1 不写能力 | 客房、灯，`capabilities` 为 `null` | 同 S0 |
| S2 能力过宽 | 客房、灯，`power`、亮度、颜色 | 同 S0 |
| S3 能力缺失 | 客房、灯，只有亮度 | 不进行写操作，报告超出范围 |
| S4 房间错误 | 卧室、灯、`power` | 不进行写操作，报告目标与范围不符 |
| S5 不写房间 | `rooms` 为 `null`，灯、`power` | 同 S0，不改变其他房间 |

- 暴露策略：`full`（对照）、`rule`、`discovered`、`retrieve`；S1 下 `rule` 无法筛选，不参与。
- 用例：C1、C3、C4、C5、C8；档位：24 与 200；模型：`spark-x2.5-1.7b`、`spark-x2.5-4b`。
- 规模：每格 20 变体 × 3 次重复，约 2.8 万次；运行前报规模与 Token 估算，由维护人批准。
- 已有依据：P-D 的可见性不使用 `scope.capabilities`，在正确范围下通过率与 `rule` 相当（见[实施进展](exposure-experiment.md#实施进展)）。

### 需要主 Agent 的实验

以下四项已确定进行（维护人确认，2026-10-15）：

| 实验 | 考察内容 | 前提 |
| --- | --- | --- |
| 子任务背景多少 | `context` 只给目标，与附带会话摘要相比，执行子 Agent 的通过率与成本差别 | 可用现有执行子 Agent 先做 |
| 失败处理 | 设备离线或拒绝执行时，主 Agent 重试、换用方式或告知用户，是否停止重派 | 仿真需支持设备故障注入 |
| 进行中修改 | 执行期间用户取消或改变要求时，未执行动作是否停止、已执行动作是否如实汇报；取消不是回滚 | Runtime 需支持执行期间接收新消息 |
| 隐含意图 | 用户不直说（如“客房好黑”“我要睡了”）时，主 Agent 是否正确判断要做什么或不做 | 主 Agent 实现 |

以下为候选，待确认：

- **分层是否值得**：单个 Agent 直接处理，与主 Agent 加子 Agent 相比，通过率、成本与时延；
- **是否委派与拆分**：闲聊、查询、多件事、带条件的请求，主 Agent 是否误派、漏派、拆分正确；
- **追问往返**：转达澄清后，用户以模拟回答补充，主 Agent 能否续派，是否替用户选择；
- **汇报如实**：注入完成、部分完成、失败及虚报完成的子任务结果，回复子 Agent 的表述是否与平台状态一致；需先确定对自然语言回复的判定方式；
- **提醒提交结果**：执行子 Agent 以文本结束时由 Runtime 提醒一次提交结构化结果，与不提醒对照。`spark-x2.5-1.7b` 在 P-D 中约四分之一的运行以文本结束。

## 待确认

- 未提交结构化结果时的整理方式（见[子任务结果处理](#子任务结果处理)）；
- 主 Agent、回复子 Agent 使用的模型，拟议主 Agent 使用 `spark-x2.5-4b`，并与执行子 Agent 的模型搭配做对照；
- 决策与回复意图的字段；
- 每次回应至少经过主 Agent 与回复子 Agent 两次模型调用，时延与成本需实测。
