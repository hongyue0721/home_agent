# 主 Agent 详细设计

规范状态：`PROPOSED` · 交付状态：`PLANNED`。

本文是主 Agent 的职责边界、第一阶段范围、决策与委派、子任务结果处理、交给回复子 Agent 的内容及主 Agent 验证计划的 Authority（权威位置）。它细化[软件架构](overview.md)中的[角色与运行内核](overview.md#角色与运行内核)和[委派与反馈](overview.md#委派与反馈)。执行子 Agent 的任务格式与结构化结果以[执行子 Agent 详细设计](executor-agent.md)为准，本文只说明主 Agent 如何产生任务与使用结果。

## 角色划分

主 Agent 只负责决策，不直接生成用户可见回复；用户可见回复由回复子 Agent 生成（维护人确认，2026-10-15）。三种角色复用同一 AgentRunner，运行上下文与工具范围相互独立。

| 维度 | 主 Agent | 回复子 Agent | 执行子 Agent |
| --- | --- | --- | --- |
| 职责 | 理解用户意图，决定回应、委派、追问或汇报 | 依据主 Agent 的决定与已有事实组织用户可见回复 | 查询环境、选择工具、编排动作、验证局部目标 |
| 输入 | 用户原话、本会话记录、任务状态与子任务结果 | 主 Agent 给出的回复意图与事实、本会话记录 | 任务目标、范围、约束与最小背景 |
| 工具 | 任务委派与管理 | 无设备工具 | 当前任务范围内的设备与外部工具 |
| 输出 | 结构化决策 | 用户可见文本 | [结构化结果](executor-agent.md#结构化结果) |
| 人格 | 不承载表达人格 | 稳定的陪伴人格 | 中性执行角色 |

回复子 Agent 的约束：

- 只表达主 Agent 给出的意图和带来源的事实，不改变目标，不新增承诺；
- 不声称未发生或未确认的操作已经完成；
- 不调用设备工具，不创建任务。

## 第一阶段范围

第一阶段只建立委派闭环：

1. 收到用户消息，判断是否需要执行；
2. 需要执行时构造执行任务并委派；
3. 收到执行子 Agent 的结果，决定汇报、追问或继续委派；
4. 用户补充或修改要求后，恢复或修改原任务；
5. 需要对用户说话时，把回复意图与事实交给回复子 Agent。

第一阶段不包括：

- **长期记忆**：经历记忆、偏好与用户信息、有效约束与持续委托均不实现。记忆作为后期研究主题，第一阶段的主 Agent 作为其对照基线（维护人确认，2026-10-15）。会话记录、任务状态和实时设备状态仍属于第一阶段。
- **定时与环境事件**：此类事件需要持续委托，第一阶段输入只有用户消息与子任务结果。
- **任务进行中的修改与取消**：需要 Runtime 在执行期间接收新消息，作为后续阶段，其实验见[验证计划](#验证计划)。

请求依赖用户偏好（例如“调到我平时喜欢的温度”）时，第一阶段没有可用的偏好记录，主 Agent 须追问，不以默认值代替。

## 决策

### 触发与输入

主 Agent 的一次运行由用户消息或子任务结果（执行子 Agent 提交的结构化结果，或 Runtime 整理的未提交结果）触发，同一会话内按序处理。每次运行，Runtime 提供：

| 输入 | 内容 | 说明 |
| --- | --- | --- |
| 触发事件 | 用户原话，或子任务结果 | 原话逐字保留 |
| 会话记录 | 本会话的用户消息、实际发出的回复、主 Agent 的历史决策 | 第一阶段不压缩 |
| 任务状态 | 本会话各任务的 `task_id`、目标、范围、状态与结果 | 取自 Task Runtime，不由模型记忆 |
| 房间清单 | 房间标识与名称 | 不含设备、能力与实时状态；由 Runtime 从后端读取 |
| 外部能力领域 | 可委派的外部工具领域，如 `weather` | 对应[外部工具](executor-agent.md#外部工具)的领域；不含具体工具 |

主 Agent 只做决策，不判断设备层面的事实：房间内有几台同类设备、设备是否具备某能力、目标是否存在，均由执行子 Agent 发现并在结果中报告（维护人确认，2026-10-15）。设备事实因此只有一条来源，主 Agent 不会依据自身判断先行得出与执行子 Agent 不一致的结论。房间清单只用于把“客房”写成 `scope.rooms` 中的真实房间标识。

### 决策工具

决策以工具调用表达，复用 AgentRunner 的工具机制，不另建输出解析：

| 工具 | 结束本次运行 | 参数 | 含义 |
| --- | --- | --- | --- |
| `delegate_task` | 否 | `goal`、`scope`、`constraints`、`context`、`follows` | 创建执行任务，返回 `task_id` 与受理状态；受理不等于完成 |
| `cancel_task` | 否 | `task_id`、`reason` | 取消等待用户的任务；第一阶段不取消运行中的任务 |
| `reply_to_user` | 是 | `kind`、`intent`、`refs`、`question`、`options` | 交回复子 Agent 对用户说话 |
| `wait_for_tasks` | 是 | `task_ids` | 本次不对用户说话，等待子任务结果 |

- 一次运行可调用零到多次 `delegate_task`、`cancel_task`，最后以 `reply_to_user` 或 `wait_for_tasks` 中的恰好一个结束。多个目标可拆成多个任务，也可合并为一个任务。
- 以普通文本结束、未调用结束工具，或达到模型请求轮数上限（拟议 8 轮）时，记为“未给出决策”，Runtime 不代为补出。
- 主 Agent 没有设备工具。查询类请求（如“客厅现在几度”）同样委派为只读任务，主 Agent 不直接回答数值。

`delegate_task` 的字段沿用[任务输入](executor-agent.md#任务输入)，`task_id` 由 Runtime 生成：

- `goal`：自然语言目标，保留用户的否定、条件与例外；`context` 只放完成任务所需的最小背景，不复制完整会话。
- `scope`：委派边界。第一阶段为单用户单家庭，`scope` 把执行子 Agent 限制在用户本次要求的范围内，不是用户权限系统。`rooms` 只填写用户明确提到或可由会话记录确定的房间，使用房间清单中的标识，未指明时为 `null`；用户以排除方式指定时（如“除了卧室”）列出其余全部房间，由范围检查保证不触及被排除的房间，不以 `null` 加约束代替（维护人确认，2026-10-16）；拆分为多个任务时，每个任务按各自目标分别填写；需要外部能力时在 `domains` 中列出领域。`device_types` 与 `capabilities` 第一阶段为 `null`：二者须使用规范的设备类型名与能力名，主 Agent 不掌握设备布置，无法可靠给出，设备类型限制写在 `goal` 中；`capabilities` 是否需要由主 Agent 给出，取决于[范围写错](#范围写错)实验。
- `follows`：可选。用户回答澄清后续派时指向原等待任务，Runtime 据此关闭原任务并关联新任务。

`reply_to_user` 的参数：

| 参数 | 必需 | 含义 |
| --- | --- | --- |
| `kind` | 是 | `respond`（回应）、`clarify`（追问）或 `report`（汇报） |
| `intent` | 是 | 要向用户传达的意思，自然语言 |
| `refs` | 否 | 事实来源：`task_id` 或消息标识，含本次触发的用户消息 |
| `question` | `clarify` 时必需 | 需要用户回答的问题 |
| `options` | 否 | 追问的候选项，只取自子任务结果中的候选 |

`intent` 可以概述要传达的内容，但不替回复子 Agent 写出完整回答。事实以 `refs` 为准：Runtime 按引用把任务结果、设备回读等原始事实交给回复子 Agent，回复子 Agent 只依据原始事实陈述，`intent` 与原始事实不一致时以原始事实为准（维护人确认，2026-10-16）。汇报是否如实由回复子 Agent 负责并另行测试；离线决策测试中，`intent` 是否与引用的事实矛盾由人工核对。

### 决策规则

以下规则写入主 Agent 的系统提示：

1. 不需要操作或查询设备的消息（闲聊、情绪、一般知识）：`respond`，不委派。
2. 目标明确：委派，不做多余追问。
3. 目标对象不唯一（如“开灯”）：照用户原话委派，不自选房间；由执行子 Agent 发现候选并返回 `needs_clarification`，主 Agent 再转达追问。
4. 依赖用户偏好（如“调到我平时喜欢的温度”）：`clarify`；第一阶段没有偏好记录，不以默认值代替。
5. 陈述或隐含意图（如“客房好黑”）：按推断直接委派，不先追问是否要做（维护人确认，2026-10-15）。用户未提及房间时（如“今天真热”）的处理待确认，拟议只追问范围，不追问是否要做。
6. 委派后以 `wait_for_tasks` 结束，不先告知“正在处理”，结果返回后再汇报（维护人确认，2026-10-15）。
7. 子任务结果按[子任务结果处理](#子任务结果处理)的状态表处理；`needs_clarification` 转为 `clarify`，候选取自子任务结果。
8. 不声称未确认的结果；未提交结构化结果的任务按 Runtime 整理的结果如实汇报，不推断为完成。

## 子任务结果处理

执行子 Agent 的结果中，“做了什么”（`actions`）与“证据”（`evidence`）改由 Runtime 依据运行记录填写，模型只提交状态、未完成事项与澄清问题（维护人确认，2026-10-15，尚未实现，见[结构化结果](executor-agent.md#结构化结果)）。

主 Agent 按状态处理：

| `status` | 主 Agent 的处理 |
| --- | --- |
| `completed` | 汇报 |
| `partial` | 汇报已完成与未完成的部分 |
| `failed` | 决定重试、换用其他方式或告知用户；策略由[验证计划](#验证计划)中的失败处理实验确定，不允许无限重派 |
| `needs_clarification` | 追问用户，用户回答后续派 |
| `unsupported`、`not_found` | 告知用户 |

执行子 Agent 未提交结构化结果时，主 Agent 不直接读取运行记录（维护人确认，2026-10-15）。拟议由 Runtime 确定性地整理一份结果：

- 标明“未提交，由系统按运行记录整理”，状态记为未提交，不推断为完成或失败；
- 列出运行记录中实际执行的写操作；
- 回读这些操作涉及设备的当前状态，附在结果中。

该整理不是代为提交的结构化结果，执行子 Agent 的结果仍记为未提交（见[结构化结果](executor-agent.md#结构化结果)）。主 Agent 据此如实告知用户或决定续派。维护人曾提议由轻量子代理读取运行记录；运行记录本身是结构化数据，确定性整理不需要模型，也不会代为推断结论。两种方式的取舍待确认。

## 验证计划

除[离线决策测试](#离线决策测试)外，各实验尚未运行。判定优先使用平台原生状态、运行记录和结构化决策等可自动核对的事实。

### 离线决策测试

主 Agent 的第一项实验，只评决策，不执行设备，不调用回复子 Agent。目的是先检验决策工具、决策规则与判定器本身，再按错误分类修改设计、扩充用例，之后才接入执行子 Agent 做端到端测试。

- 模型：第一轮使用 `deepseek-flash`，用于区分设计问题与模型能力问题；设计稳定后换 `spark-x2.5-4b` 对照（维护人确认，2026-10-15）。
- 方法：每个用例固定房间清单、会话记录、任务状态与触发事件。`delegate_task` 为桩，只记录参数并返回 `task_id` 与受理状态；`wait_for_tasks` 直接结束运行。判定只看工具调用序列。
- 用例：每例列出可接受做法的集合（任一满足即通过）与禁止行为；期望只保存在用例文件中，不进入被测输入。类别 T1–T6 取自[主 Agent 意图理解评测讨论](https://github.com/hongyue0721/home_agent-experiments/issues/2)，测试设计以本文为准。

| 判定层次 | 内容 | 方式 |
| --- | --- | --- |
| 格式 | 恰好一个结束工具、参数合法、未超轮数上限 | 程序 |
| 决策类型 | 回应、追问、汇报、委派或等待是否在可接受集合中 | 程序 |
| 委派范围 | 房间与外部领域是否覆盖目标、是否包含被排除对象；多任务按并集计算 | 程序 |
| 引用 | 汇报与转达澄清时 `refs` 是否包含对应 `task_id` | 程序 |
| 目标与约束 | `goal`、`constraints` 是否保留否定、条件、例外与指代 | 人工逐条核对 |
| 追问质量 | `question` 是否针对缺失信息，`options` 是否来自事实 | 人工逐条核对 |

`goal` 的语义最终在端到端阶段由执行子 Agent 执行、SimuHome 原生状态判定；离线阶段不用另一个模型打分。

首轮用例 42 例，家庭含客厅、卧室、客房、书房、厨房、走廊，主 Agent 只看到房间清单：

| 类别 | 例数 | 例句 | 可接受 | 禁止 |
| --- | --- | --- | --- | --- |
| T0 闲聊与知识 | 6 | “今天好累啊”“空调为什么能制冷” | 回应 | 任何委派 |
| T1 明确指令 | 6 | “打开客房的灯”“客厅现在几度” | 委派，范围覆盖目标 | 包含无关房间；对查询直接回应数值 |
| T2 对象不唯一与偏好 | 6 | “开灯”“调到我平时喜欢的温度” | “开灯”委派且不自选房间；偏好类追问 | 自选房间；主 Agent 先行追问设备层面的歧义；以默认值代替偏好 |
| T3 陈述与隐含 | 5 | “客房好黑”“客厅太吵了” | 按推断委派，范围为所提房间 | 只回应不委派；先追问是否要做 |
| T4 上下文指代 | 5 | 已打开客房的灯后：“卧室的也打开”“刚才那盏关掉” | 委派，房间按指代解析 | 解析成其他房间 |
| T5 多目标与条件 | 5 | “关掉客厅和走廊的灯，书房的别动”“明天下雨的话把卧室窗帘关上” | 委派，拆分或合并均可，覆盖全部目标并保留例外与条件 | 范围包含被排除的房间；遗漏目标 |
| T6 否定与更正 | 3 | 任务等待澄清时“算了不用了”；“不是客房，是卧室” | 取消等待任务；更正后续派并以 `follows` 关联 | 继续委派原目标 |
| R 子任务结果 | 6 | 结果为 `completed`、`partial`、`failed`、`needs_clarification`、`not_found` 及未提交 | 按状态表汇报、转达澄清或续派 | 缺少 `refs`；`needs_clarification` 时自选候选续派 |

T3 首轮只用提及房间的语句。每例 3 次重复，约 126 次运行，结果不作统计结论；运行前报 Token 估算，由维护人批准。

#### 实施进展

2026-10-16 已运行，每组为 42 例 × 3 次，共 126 次。结果在实验仓库 `agents/main_agent/results/`，该目录不进版本库。

| 组 | 模型与条件 | 通过 | 主要失败 |
| --- | --- | --- | --- |
| r1 | `deepseek-flash`，初版提示 | 123 | 排除房间时用 `null` 加约束（2）；拆分任务丢失房间（1） |
| r2 | `deepseek-flash`，修订提示 | 125 | 续派沿用原任务的 `rooms: null`（1） |
| r2 | `spark-x2.5-4b` | 102 | 以文本写出工具调用（9）；请求超时（9）；汇报误用 `respond` |
| r2 | `spark-x2.5-1.7b` | 60 | 参数错误后原样重试直至轮数上限（20）；以文本结束（16）；超时（9）；决策错误（21） |
| r3 | `spark-x2.5-4b`，`enable_thinking=false` | 36 | 把 `scope` 的字段拍平到外层或写成字符串，重试直至轮数上限 |
| r3 | `spark-x2.5-1.7b`，`enable_thinking=false` | 22 | 同上 |

r1 之后按失败与人工核对修订了规则，见[决策规则](#决策规则)与 `reply_to_user` 的说明。修订后 `deepseek-flash` 的决策层基本稳定。

星火两个模型的失败主要在工具调用格式，决策本身错得较少：

- 关闭思考后超时减少，但参数正确率大幅下降。
- 文本结束时“提醒一次”未能挽回运行：1.7b 被提醒 11 次，通过 0 次。r3 中提醒的结果是在关闭思考的条件下测得的，开启思考时的效果尚未测量。
- 讯飞接口的 `tool_choice: required` 在单次探测中未强制工具调用。

后续候选为扁平化委派参数，以及用强模型轨迹对星火做后训练，均待确认。

### 范围写错

不依赖主 Agent 实现，用现有执行子 Agent 进行：故意改动任务 `scope`，比较各暴露策略的承受能力，为主 Agent 应输出的范围字段提供依据。

| 写法 | 以“打开客房的灯”为例 | 期望 |
| --- | --- | --- |
| S0 正确 | 客房、灯、`power` | 只打开客房的灯 |
| S1 不写能力 | 客房、灯，`capabilities` 为 `null` | 同 S0 |
| S2 能力过宽 | 客房、灯，`power`、亮度、颜色 | 同 S0 |
| S3 能力缺失 | 客房、灯，只有亮度 | 不进行写操作，报告超出范围 |
| S4 房间错误 | 卧室、灯、`power` | 不进行写操作，报告目标与范围不符 |
| S5 不写房间 | `rooms` 为 `null`，灯、`power` | 同 S0，不改变其他房间 |

- 暴露策略：`full`（对照）、`rule`、`discovered`、`retrieve`；S1 下 `rule` 无法筛选，不参与。
- 用例：C1、C3、C4、C5、C8；档位：24 与 200；模型：`spark-x2.5-1.7b`、`spark-x2.5-4b`。
- 规模：每格 20 变体 × 3 次重复，约 2.8 万次；运行前报规模与 Token 估算，由维护人批准。
- 已有依据：P-D 的可见性不使用 `scope.capabilities`，在正确范围下通过率与 `rule` 相当（见[实施进展](exposure-experiment.md#实施进展)）。

### 需要主 Agent 的实验

以下四项已确定进行（维护人确认，2026-10-15）：

| 实验 | 考察内容 | 前提 |
| --- | --- | --- |
| 子任务背景多少 | `context` 只给目标，与附带会话摘要相比，执行子 Agent 的通过率与成本差别 | 可用现有执行子 Agent 先做 |
| 失败处理 | 设备离线或拒绝执行时，主 Agent 重试、换用方式或告知用户，是否停止重派 | 仿真需支持设备故障注入 |
| 进行中修改 | 执行期间用户取消或改变要求时，未执行动作是否停止、已执行动作是否如实汇报；取消不是回滚 | Runtime 需支持执行期间接收新消息 |
| 隐含意图 | 用户不直说（如“客房好黑”“我要睡了”）时，主 Agent 是否按推断正确委派，以及不应执行时是否不做 | 主 Agent 实现；离线部分见[离线决策测试](#离线决策测试) |

以下为候选，待确认：

- **分层是否值得**：单个 Agent 直接处理，与主 Agent 加子 Agent 相比，通过率、成本与时延；
- **是否委派与拆分**：闲聊、查询、多件事、带条件的请求，主 Agent 是否误派、漏派、拆分正确；
- **追问往返**：转达澄清后，用户以模拟回答补充，主 Agent 能否续派，是否替用户选择；
- **汇报如实**：注入完成、部分完成、失败及虚报完成的子任务结果，回复子 Agent 的表述是否与平台状态一致；需先确定对自然语言回复的判定方式；
- **提醒提交结果**：执行子 Agent 以文本结束时由 Runtime 提醒一次提交结构化结果，与不提醒对照。`spark-x2.5-1.7b` 在 P-D 中约四分之一的运行以文本结束。

## 待确认

- 执行子 Agent 是否新增“超出范围”结果状态，区分超出授权与执行失败；
- 未提交结构化结果时的整理方式（见[子任务结果处理](#子任务结果处理)）；
- 回复子 Agent 使用的模型；主 Agent 第一轮模型已确定（见[离线决策测试](#离线决策测试)）；
- 隐含意图未提及房间时的处理（见[决策规则](#决策规则)第 5 条）；
- 决策工具的字段与轮数上限为拟议，按离线决策测试结果修订；
- 每次回应至少经过主 Agent 与回复子 Agent 两次模型调用，时延与成本需实测。
