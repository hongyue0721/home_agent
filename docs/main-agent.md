# 主 Agent 详细设计

规范状态：`PROPOSED` · 交付状态：`PLANNED`。

本文是主 Agent 的职责边界、第一阶段范围、决策与委派、子任务结果处理、交给回复子 Agent 的内容及主 Agent 验证计划的 Authority（权威位置）。它细化[软件架构](overview.md)中的[角色与运行内核](overview.md#角色与运行内核)和[委派与反馈](overview.md#委派与反馈)。执行子 Agent 的任务格式与结构化结果以[执行子 Agent 详细设计](executor-agent.md)为准，本文只说明主 Agent 如何产生任务与使用结果。

## 角色划分

主 Agent 负责决策；简单请求由主 Agent 直接调用家居工具办理，需要时才委派执行子 Agent，见[直办与按需委派](#直办与按需委派)。主 Agent 不直接生成用户可见回复，用户可见回复由回复子 Agent 生成（维护人确认，2026-10-15）。三种角色复用同一 AgentRunner，运行上下文与工具范围相互独立。

| 维度 | 主 Agent | 回复子 Agent | 执行子 Agent |
| --- | --- | --- | --- |
| 职责 | 理解用户意图，决定回应、直办、委派、追问或汇报 | 依据主 Agent 的决定与已有事实组织用户可见回复 | 查询环境、选择工具、编排动作、验证局部目标 |
| 输入 | 用户原话、本会话记录、任务状态与子任务结果 | 主 Agent 给出的回复意图与事实、本会话记录 | 任务目标、范围、约束与最小背景 |
| 工具 | 家居工具（直办）、任务委派与管理 | 无设备工具 | 当前任务范围内的设备与外部工具 |
| 输出 | 结构化决策 | 用户可见文本 | [结构化结果](executor-agent.md#结构化结果) |
| 人格 | 不承载表达人格 | 稳定的陪伴人格 | 中性执行角色 |

回复子 Agent 的约束：

- 只表达主 Agent 给出的意图和带来源的事实，不改变目标，不新增承诺；
- 不声称未发生或未确认的操作已经完成；
- 不调用设备工具，不创建任务。

## 第一阶段范围

第一阶段只建立委派闭环，已实现并作为验证基线。其中“需要执行时一律委派”的做法由[直办与按需委派](#直办与按需委派)取代（维护人确认，2026-10-16）；本节与[委派闭环](#委派闭环)描述的委派机制保留，供按需委派使用。


1. 收到用户消息，判断是否需要执行；
2. 需要执行时构造执行任务并委派；
3. 收到执行子 Agent 的结果，决定汇报、追问或继续委派；
4. 用户补充或修改要求后，恢复或修改原任务；
5. 需要对用户说话时，把回复意图与事实交给回复子 Agent。

第一阶段不包括：

- **长期记忆**：经历记忆、偏好与用户信息、有效约束与持续委托均不实现。记忆作为后期研究主题，第一阶段的主 Agent 作为其对照基线（维护人确认，2026-10-15）。会话记录、任务状态和实时设备状态仍属于第一阶段。
- **定时与环境事件**：此类事件需要持续委托，第一阶段输入只有用户消息与子任务结果。
- **任务进行中的修改与取消**：需要 Runtime 在执行期间接收新消息，作为后续阶段，其实验见[验证计划](#验证计划)。

请求依赖用户偏好（例如“调到我平时喜欢的温度”）时，第一阶段没有可用的偏好记录，主 Agent 须追问，不以默认值代替。

## 决策

### 触发与输入

主 Agent 的一次运行由用户消息或子任务结果（执行子 Agent 提交的结构化结果，或 Runtime 整理的未提交结果）触发，同一会话内按序处理。每次运行，Runtime 提供：

| 输入 | 内容 | 说明 |
| --- | --- | --- |
| 触发事件 | 用户原话，或子任务结果 | 原话逐字保留 |
| 会话记录 | 本会话的用户消息、实际发出的回复、主 Agent 的历史决策 | 第一阶段不压缩 |
| 任务状态 | 本会话各任务的 `task_id`、目标、范围、状态与结果 | 取自 Task Runtime，不由模型记忆 |
| 房间清单 | 房间标识与名称 | 不含设备、能力与实时状态；由 Runtime 从后端读取 |
| 外部能力领域 | 可委派的外部工具领域，如 `weather` | 对应[外部工具](executor-agent.md#外部工具)的领域；不含具体工具 |

主 Agent 不凭自身判断认定设备层面的事实：房间内有几台同类设备、设备是否具备某能力、目标是否存在，只来自经 Runtime 调用的工具返回（维护人确认，2026-10-15）。第一阶段由执行子 Agent 发现并在结果中报告；直办时来自主 Agent 自己的工具调用。设备事实因此只有工具返回这一条来源。房间清单只用于把“客房”写成 `scope.rooms` 中的真实房间标识。

### 决策工具

决策以工具调用表达，复用 AgentRunner 的工具机制，不另建输出解析：

| 工具 | 结束本次运行 | 参数 | 含义 |
| --- | --- | --- | --- |
| `delegate_task` | 否 | `goal`、`scope`、`constraints`、`context`、`follows` | 创建执行任务，返回 `task_id` 与受理状态；受理不等于完成 |
| `cancel_task` | 否 | `task_id`、`reason` | 取消等待用户的任务；第一阶段不取消运行中的任务 |
| `reply_to_user` | 是 | `kind`、`intent`、`refs`、`question`、`options` | 交回复子 Agent 对用户说话 |
| `wait_for_tasks` | 是 | `task_ids` | 本次不对用户说话，等待子任务结果 |

- 一次运行可调用零到多次 `delegate_task`、`cancel_task`，最后以 `reply_to_user` 或 `wait_for_tasks` 中的恰好一个结束。多个目标可拆成多个任务，也可合并为一个任务。
- 以普通文本结束、未调用结束工具，或达到模型请求轮数上限（拟议 8 轮）时，记为“未给出决策”，Runtime 不代为补出。
- 第一阶段主 Agent 没有设备工具，查询类请求（如“客厅现在几度”）同样委派为只读任务。直办后改为主 Agent 直接查询，数值取自工具返回。

`delegate_task` 的字段沿用[任务输入](executor-agent.md#任务输入)，`task_id` 由 Runtime 生成：

- `goal`：自然语言目标，保留用户的否定、条件与例外；`context` 只放完成任务所需的最小背景，不复制完整会话。
- `scope`：委派边界。第一阶段为单用户单家庭，`scope` 把执行子 Agent 限制在用户本次要求的范围内，不是用户权限系统。`rooms` 只填写用户明确提到或可由会话记录确定的房间，使用房间清单中的标识，未指明时为 `null`；用户以排除方式指定时（如“除了卧室”）列出其余全部房间，由范围检查保证不触及被排除的房间，不以 `null` 加约束代替（维护人确认，2026-10-16）；拆分为多个任务时，每个任务按各自目标分别填写；需要外部能力时在 `domains` 中列出领域。`device_types` 与 `capabilities` 第一阶段为 `null`：二者须使用规范的设备类型名与能力名，主 Agent 不掌握设备布置，无法可靠给出，设备类型限制写在 `goal` 中；[范围写错](#范围写错)实验后，执行子 Agent 选用 P-D，不要求 `capabilities`；正确的能力对小模型有帮助，是否补全待确认。
- `follows`：可选。用户回答澄清后续派时指向原等待任务，Runtime 据此关闭原任务并关联新任务。

`reply_to_user` 的参数：

| 参数 | 必需 | 含义 |
| --- | --- | --- |
| `kind` | 是 | `respond`（回应）、`clarify`（追问）或 `report`（汇报） |
| `intent` | 是 | 要向用户传达的意思，自然语言 |
| `refs` | 否 | 事实来源：`task_id` 或消息标识，含本次触发的用户消息 |
| `question` | `clarify` 时必需 | 需要用户回答的问题 |
| `options` | 否 | 追问的候选项，只取自工具返回或子任务结果中的候选 |

`intent` 可以概述要传达的内容，但不替回复子 Agent 写出完整回答。事实以 `refs` 为准：Runtime 按引用把任务结果、设备回读等原始事实交给回复子 Agent，回复子 Agent 只依据原始事实陈述，`intent` 与原始事实不一致时以原始事实为准（维护人确认，2026-10-16）。汇报是否如实由回复子 Agent 负责并另行测试；离线决策测试中，`intent` 是否与引用的事实矛盾由人工核对。

### 决策规则

以下规则写入主 Agent 的系统提示：

1. 不需要操作或查询设备的消息（闲聊、情绪、一般知识）：`respond`，不委派。
2. 目标明确：委派，不做多余追问。
3. 目标对象不唯一（如“开灯”）：照用户原话委派，不自选房间；由执行子 Agent 发现候选并返回 `needs_clarification`，主 Agent 再转达追问。
4. 依赖用户偏好（如“调到我平时喜欢的温度”）：`clarify`；第一阶段没有偏好记录，不以默认值代替。
5. 陈述或隐含意图（如“客房好黑”）：按推断直接委派，不先追问是否要做（维护人确认，2026-10-15）。用户未提及房间时（如“今天真热”）的处理待确认，拟议只追问范围，不追问是否要做。
6. 委派后以 `wait_for_tasks` 结束，不先告知“正在处理”，结果返回后再汇报（维护人确认，2026-10-15）。
7. 子任务结果按[子任务结果处理](#子任务结果处理)的状态表处理；`needs_clarification` 转为 `clarify`，候选取自子任务结果。
8. 不声称未确认的结果；未提交结构化结果的任务按 Runtime 整理的结果如实汇报，不推断为完成。

## 子任务结果处理

执行子 Agent 的结果中，“做了什么”（`actions`）与“证据”（`evidence`）由 Runtime 依据运行记录填写，模型只提交状态、未完成事项与澄清问题（维护人确认，2026-10-15）；已实现为执行子 Agent 的默认行为，见[结构化结果](executor-agent.md#结构化结果)。被范围检查拒绝的调用以错误码 `out_of_scope` 记入 `evidence`，主 Agent 据此区分超出范围与执行失败，不另设结果状态（维护人确认，2026-10-16）。

主 Agent 按状态处理：

| `status` | 主 Agent 的处理 |
| --- | --- |
| `completed` | 汇报 |
| `partial` | 汇报已完成与未完成的部分 |
| `failed` | 决定重试、换用其他方式或告知用户；策略由[验证计划](#验证计划)中的失败处理实验确定，不允许无限重派 |
| `needs_clarification` | 追问用户，用户回答后续派 |
| `unsupported`、`not_found` | 告知用户 |

执行子 Agent 未提交结构化结果时，主 Agent 不直接读取运行记录（维护人确认，2026-10-15），由 Runtime 确定性地整理一份结果（维护人确认，2026-10-16）：

- 标明“未提交，由系统按运行记录整理”，状态记为未提交，不推断为完成或失败；
- 列出运行记录中实际执行的写操作；
- 回读这些操作涉及设备的当前状态，附在结果中。

该整理不是代为提交的结构化结果，执行子 Agent 的结果仍记为未提交（见[结构化结果](executor-agent.md#结构化结果)）。主 Agent 据此如实告知用户或决定续派。维护人曾提议由轻量子代理读取运行记录；运行记录本身是结构化数据，确定性整理不需要模型，也不会代为推断结论，因此采用确定性整理。

整理结果的格式沿用离线决策测试的输入：`submitted` 为 `false`，`writes` 为已交给后端执行的写调用（取舍规则同[结果提交](executor-agent.md#结果提交-report_result)中 `actions` 的计算），`readback` 为这些调用涉及设备在运行结束后的状态，由 Runtime 经设备后端读取。

### 调用内容展开

`actions` 与 `evidence` 只是工具调用标识，主 Agent 又不读取运行记录，因此执行子 Agent 查到的信息（天气、温度、设备当前状态）到不了主 Agent。首轮端到端测试中，E9 的主 Agent 先委派查询天气，收到 `completed` 与一个调用标识，无法判断是否下雨。采用 Runtime 展开：Runtime 把调用内容附在结果中，由主 Agent 读取原始返回并自行得出结论；执行子 Agent 不另写结论（维护人确认，2026-10-16）。困难的理解与判断由主 Agent 承担，执行子 Agent 提交的内容不变，事实全部来自运行记录。

- Runtime 把任务结果交给主 Agent 时（任务记录中的 `result` 与 `task_results` 触发），增加 `observations` 字段。执行子 Agent 的 `report_result` 参数与[结构化结果](executor-agent.md#结构化结果)不变。
- 收录：`actions` 与 `evidence` 引用的全部调用；以及成功的 `get_device_state`、`get_room_environment` 调用。外部工具在目录中归为操作工具，经 `actions` 收录。不收录发现工具（`get_rooms`、`get_room_devices`、`list_all_devices`）与 `get_device_capabilities`：前者是清单，后者是能力描述，篇幅大且不含查询结论。
- 每项含 `call_id`、`tool`、`arguments`、`ok`；成功时 `result` 为工具返回给执行子 Agent 的内容，失败时为 `error`。按运行记录顺序排列；同一工具、同一参数的成功读取只保留最后一次，被 `actions` 或 `evidence` 引用的调用全部保留。
- 未提交结果的整理同样附 `observations`，规则相同，`writes` 与 `readback` 不变。
- 主 Agent 依据 `observations` 得出结论（如是否下雨、温度数值），汇报时只陈述其中出现的内容，不补充推测；该规则写入系统提示。
- 首轮不设长度截断；端到端测试按主 Agent 输入 Token 观察，过长时再定截断方式。
- 离线决策测试中含任务结果的用例同步增加该字段。

## 委派闭环

本节是第一阶段的委派闭环：`delegate_task` 实际交给执行子 Agent 执行，结果回到主 Agent，再决定汇报、追问或续派。它细化[任务边界](overview.md#任务边界)与[委派与反馈](overview.md#委派与反馈)在第一阶段的取舍；任务进行中的修改与取消不在本节范围内。

### 任务状态

Task Runtime 为每个会话维护任务记录：`task_id`（Runtime 生成，会话内唯一）、`goal`、`scope`、`constraints`、`context`、`follows`、引出该任务的用户消息、状态与结果。状态如下：

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| `accepted` | 已受理，尚未执行 | `delegate_task` 校验通过 |
| `running` | 执行子 Agent 运行中 | Runtime 开始执行 |
| `completed`、`partial`、`failed`、`unsupported`、`not_found` | 已结束 | 执行子 Agent 提交相应 `status` |
| `waiting_user` | 等待用户回答 | 执行子 Agent 提交 `needs_clarification` |
| `unsubmitted` | 已结束，未提交结构化结果 | 运行未以合法的 `report_result` 结束，结果为 Runtime 的整理 |
| `cancelled` | 已取消 | 主 Agent 对 `waiting_user` 任务调用 `cancel_task`；或所属的主 Agent 运行未给出决策 |
| `superseded` | 已由续派任务接替 | 新任务以 `follows` 指向该 `waiting_user` 任务 |

- 状态与转换按上表执行，含 `superseded`（维护人确认，2026-10-16）。
- `cancel_task` 与 `follows` 只接受 `waiting_user` 的任务，否则按参数错误返回给主 Agent。
- `waiting_user` 是唯一可恢复的状态；恢复方式是续派新任务，原任务不重新运行。
- 结束状态不再改变。执行子 Agent 运行异常（模型服务错误等）时记为 `unsubmitted`，Runtime 照常整理结果，并在任务记录中保留异常信息。

### 一轮处理

一条用户消息引出的全部处理称为一轮：

1. Runtime 以用户消息触发主 Agent 运行。
2. 运行以决策结束后，Runtime 按委派顺序**串行**执行本次运行中受理的任务（维护人确认，2026-10-16）。第一阶段只有一个家庭后端，串行避免任务之间互相干扰，结果可复现。
3. 本次委派的任务全部结束后，Runtime 以这批任务的结果一次性触发下一次主 Agent 运行，触发事件为 `task_results`，按委派顺序列出各任务的 `task_id` 与结果（维护人确认，2026-10-16）。离线决策测试中只含一个结果的 `task_result` 视为其特例。
4. 重复第 2、3 步，直到某次运行以 `reply_to_user` 结束且没有本次委派的任务，本轮结束。

- 运行以 `reply_to_user` 结束但本次有委派时，先交付回复，再执行任务；按[决策规则](#决策规则)第 6 条这属于违规决策，端到端测试计为决策错误（维护人确认，2026-10-16）。
- 运行未给出决策（以普通文本结束、达到轮数上限或运行异常）时，本次受理的任务不执行，记为 `cancelled`，本轮结束，并记录为“未给出决策”。Runtime 不代为补出决策，也不执行未经决策确认的任务（维护人确认，2026-10-16）。
- 每轮委派总数上限为 3（维护人确认，2026-10-16），按端到端测试结果修订。达到上限后 `delegate_task` 返回错误，说明须向用户汇报，运行继续。`wait_for_tasks` 只能等待本次运行新委派的任务，因此一轮内的主 Agent 运行次数不超过委派上限加一，不需另设运行次数上限。
- `reply_to_user` 以 `clarify` 结束时，相应任务保持 `waiting_user`；用户的下一条消息开始新的一轮，主 Agent 可以续派（`follows`）、取消或另作处理。

### 执行子 Agent 配置

闭环中的执行子 Agent 使用[选型](exposure-experiment.md#选型)确定的 P-D（`progressive` + `discovered`），[结果提交](executor-agent.md#结果提交-report_result)的三个选项取默认值。Runtime 把 `delegate_task` 的参数原样转为[任务输入](executor-agent.md#任务输入)，补上 `task_id`；`scope` 中 `device_types` 与 `capabilities` 按主 Agent 的输出保持 `null`。

### 会话记录

主 Agent 每次运行的会话记录包含本会话的用户消息与已交付的回复；任务状态取自 Task Runtime 的任务记录，含已结束、等待用户、已取消与已接替的任务。回复子 Agent 实现前，交付的回复以桩代替：`clarify` 取 `question`，其余取 `intent`，并在记录中标明为桩。

## 直办与按需委派

规范状态：`PROPOSED`，方向经维护人确认（2026-10-16）· 交付状态：`PLANNED`，按下文 P1 先实现。

### 依据

端到端测试的对照（见[批次结果](#批次结果)）表明，单轮请求一律委派并不带来更高的通过率：同一模型单独执行与“同模型委派”的家里结果正确数相当，但委派多一次交接，Token 约多 75%，耗时更长；委派给 `spark-x2.5-4b` 时通过率还更低。委派的收益在于隔离上下文、并行、把长而机械的工作交给更便宜的模型，以及长时等待，不在单轮理解。因此主 Agent 默认直接办理，只在这些情形委派（维护人确认，2026-10-16）。不保留“一律委派”的运行模式；其结果保留在已归档的批次与提交中。

### 家居工具

- 主 Agent 获得与执行子 Agent 相同的家居工具：发现、读取与写入工具，按 P-D（`progressive` + `discovered`）暴露，经同一 Tool Executor 执行，范围检查与写后回读不变。不提供 `report_result` 与 `request_tools`。
- 直办的执行范围为会话级范围：P1 在仿真中为全屋家庭设备，外部工具领域为会话开放的领域。真实设备接入前须先解决[可信授权](https://github.com/hongyue0721/home_agent-experiments/issues/13)，模型给出的范围不作为授权。
- 直办的写操作在调用时即执行。“未给出决策时不执行受理任务”只适用于委派；主 Agent 运行未给出决策时，已执行的直办操作照实记录，不回滚。

### 直办记录

- 主 Agent 一次运行中调用了家居工具时，无论运行是否给出决策，Runtime 在运行结束时把这些调用记为一条任务记录：`task_id` 由 Runtime 现有的任务标识生成；`origin` 为 `main`（委派任务为 `executor`）；状态为 `direct`（结束状态，表示主 Agent 直办，没有结构化结果状态）；`goal`、`constraints`、`context`、`follows` 与 `error` 为 `null`，`scope` 为会话级范围，关联引出该运行的用户消息。
- 结果由 Runtime 确定性生成，格式同未提交结果的整理：`writes`、`readback` 与 `observations`，规则见[子任务结果处理](#子任务结果处理)与[调用内容展开](#调用内容展开)，只计家居工具调用，不计决策工具。主 Agent 不另行提交结果；办理是否完成由主 Agent 在回复中依据 `observations` 说明。
- 直办记录在本次运行给出决策时尚不存在，主 Agent 无法在同一运行中引用。运行以 `reply_to_user` 结束时，Runtime 在交付前把本轮（同一条用户消息引出的全部主 Agent 运行，含本次）产生、尚未出现在 `refs` 中的直办记录标识按生成顺序追加到该回复的 `refs`，交付记录与事件中可见；决策参数本身与 `refs` 校验规则不变。先直办发现、再委派、待结果后汇报时，前一次运行的直办记录因此也被引用（维护人确认，2026-10-16）。之后的运行可在 `tasks` 中看到直办记录并照常引用。
- 回复子 Agent、会话记录与判定把直办记录按任务处理，不另设通道。

### 会话记录压缩

- 同一次运行内，主 Agent 看到自己工具调用的完整返回。
- 运行结束后，进入任务状态与后续运行输入的只有直办记录，原始工具消息不再带入后续运行。会话记录的增长因此与委派时相当，不随直办调用的返回长度增长。

### 委派条件

以下情形委派执行子 Agent，其余直接办理；该规则写入系统提示，Runtime 记录每次运行是否委派，供评估：

1. 互不相关、可并行的多项工作（需 Runtime 支持并行，P2）；
2. 步骤多而机械的批量工作，可交给更便宜的执行模型；
3. 需等待较长时间或事件的工作（需事件触发，P3）；
4. 需开放大量外部工具、会明显挤占主 Agent 上下文的工作。

委派沿用[委派闭环](#委派闭环)与[执行子 Agent 配置](#执行子-agent-配置)，执行模型可单独配置。

### 决策规则的调整

[决策规则](#决策规则)在 P1 中相应改写：第 2 条“目标明确”改为直接办理或按委派条件委派；第 3 条“目标对象不唯一”时，直办由主 Agent 依据发现结果追问，`options` 取自工具返回；直办后以 `report` 汇报并引用直办记录。增加一条：`question` 与 `intent` 只陈述工具返回或任务结果中出现的内容，与回复子 Agent 的[事实优先](reply-agent.md#输出约束)一致；两者仍冲突时，回复子 Agent 以引用事实为准，只问出需要用户确认的部分（维护人确认，2026-10-16）。其余条目不变。

### 回复类型与格式容错

规范状态：`PROPOSED`（维护人确认，2026-10-17）。目标模型暂为 `qwen3.7-flash`；它在 [P1 结果](#p1-结果)中的失败多集中在 `respond` 与 `report` 的区分，以及 `options` 的格式。

- 回复类型：会话中运行以 `reply_to_user` 结束且 `kind` 为 `respond` 或 `report` 时，交付的类型由 Runtime 确定。Runtime 先按[直办记录](#直办记录)追加 `refs`，之后 `refs` 中含任务标识（委派任务或直办记录，不限本轮）为 `report`，否则为 `respond`。`clarify` 不变，是否追问仍由主 Agent 决定。模型给出的原值记为 `model_kind`，与交付类型不同时记一条事件。决策工具的参数与离线决策测试不变。
- 格式容错：`reply_to_user` 的 `options` 是可解码为字符串列表的 JSON 字符串时，按该列表处理；`options` 或 `question` 为字符串 `"None"` 或 `"null"` 时，按 `null` 处理。只做这两种还原，其他不合法的值照常拒绝，例如单个字符串不包成列表。还原在校验之前进行，`clarify` 的 `question` 还原为 `null` 后照常因缺失被拒；每次还原都记入决策记录与事件。`delegate_task.follows` 的字符串 `"null"` 仍按参数错误拒绝（见[批次结果](#批次结果)第 3 轮）。
- 判定：每次决策与闭环只区分 `clarify` 与非 `clarify`；`respond` 与 `report` 由 Runtime 确定，以单元测试验证，批次中统计 `model_kind` 与交付类型不同的次数及格式还原次数。

## 验证计划

除[离线决策测试](#离线决策测试)、[范围写错](#范围写错)与[端到端测试](#端到端测试)外，各实验尚未运行。判定优先使用平台原生状态、运行记录和结构化决策等可自动核对的事实。

### 离线决策测试

主 Agent 的第一项实验，只评决策，不执行设备，不调用回复子 Agent。目的是先检验决策工具、决策规则与判定器本身，再按错误分类修改设计、扩充用例，之后才接入执行子 Agent 做端到端测试。

- 模型：第一轮使用 `deepseek-flash`，用于区分设计问题与模型能力问题；设计稳定后换 `spark-x2.5-4b` 对照（维护人确认，2026-10-15）。
- 方法：每个用例固定房间清单、会话记录、任务状态与触发事件。`delegate_task` 为桩，只记录参数并返回 `task_id` 与受理状态；`wait_for_tasks` 直接结束运行。判定只看工具调用序列。
- 用例：每例列出可接受做法的集合（任一满足即通过）与禁止行为；期望只保存在用例文件中，不进入被测输入。类别 T1–T6 取自[主 Agent 意图理解评测讨论](https://github.com/hongyue0721/home_agent-experiments/issues/2)，测试设计以本文为准。

| 判定层次 | 内容 | 方式 |
| --- | --- | --- |
| 格式 | 恰好一个结束工具、参数合法、未超轮数上限 | 程序 |
| 决策类型 | 回应、追问、汇报、委派或等待是否在可接受集合中 | 程序 |
| 委派范围 | 房间与外部领域是否覆盖目标、是否包含被排除对象；多任务按并集计算 | 程序 |
| 引用 | 汇报与转达澄清时 `refs` 是否包含对应 `task_id` | 程序 |
| 目标与约束 | `goal`、`constraints` 是否保留否定、条件、例外与指代 | 人工逐条核对 |
| 追问质量 | `question` 是否针对缺失信息，`options` 是否来自事实 | 人工逐条核对 |

`goal` 的语义最终在端到端阶段由执行子 Agent 执行、SimuHome 原生状态判定；离线阶段不用另一个模型打分。

| --- | --- | --- | --- | --- |
| T0 闲聊与知识 | 6 | “今天好累啊”“空调为什么能制冷” | 回应 | 任何委派 |
| T1 明确指令 | 6 | “打开客房的灯”“客厅现在几度” | 委派，范围覆盖目标 | 包含无关房间；对查询直接回应数值 |

### 范围写错

不依赖主 Agent 实现，用现有执行子 Agent 进行：故意改动任务 `scope`，比较各暴露策略的承受能力，为主 Agent 应输出的范围字段提供依据。

| 写法 | 以“打开客房的灯”为例 | 期望 |
| --- | --- | --- |
| S0 正确 | 客房、灯、`power` | 只打开客房的灯 |
| S1 不写能力 | 客房、灯，`capabilities` 为 `null` | 同 S0 |
| S2 能力过宽 | 客房、灯，`power`、亮度、颜色 | 同 S0 |
| S3 能力缺失 | 客房、灯，只有亮度 | 不进行写操作，报告超出范围 |
| S4 房间错误 | 卧室、灯、`power`；单房间场景用不存在的房间 | 不进行写操作，报告目标与范围不符 |
| S5 不写房间 | `rooms` 为 `null`，灯、`power` | 同 S0，不改变其他房间 |

- 暴露策略：只比较渐进发现下的 `rule` 与 P-D（`discovered`）；S1 下 `rule` 无法筛选，不参与。`full`、`retrieve` 不参与（维护人确认，2026-10-15）。
- 用例：C1、C3、C4、C5、C8，S4、S5 只用 C1、C3、C4；档位：24（`rule` 与 P-D 下 C 类用例的 `scope.domains` 为空，200 档的可见工具与 24 档相同）；模型：`spark-x2.5-1.7b`、`spark-x2.5-4b`。
- 规模：每格 20 变体 × 3 次重复，11 组共 5,640 次。
- 判定：S3、S4 通过的条件是没有写入，且报告状态不是 `completed` 或 `partial`；目标设备上被范围检查拒绝的写调用不计越界。S4 记录替换的房间是否存在。

- **能力写错时 `rule` 失去所需工具。** S3 中 `rule` 按 `scope.capabilities` 只暴露 `set_brightness`，开关所需的 `set_device_power` 不可见，`spark-x2.5-4b` 多在推理中超时（112 次）或未提交报告；P-D 按设备实际能力暴露工具，写调用被范围检查拒绝后多数如实报告。两种策略的设备状态都正确。
- **房间写成另一个现有房间时，执行层无法发现。** S4 中 P-D 与 `rule` 各有 6 次在错误房间写入，均为替换成现有房间的情形；范围检查按写错的范围放行。两种策略在 S4 的通过率相当。
- **正确的能力字段对 `spark-x2.5-1.7b` 有帮助。** P-D 下 S1 比 S0 低 12 个百分点，区间不重叠；任务 JSON 中的 `capabilities` 同时起提示作用，S1 的 C4 中模型在开启电源后又调用 `control_playback` 或设置风扇模式。`spark-x2.5-4b` 差别在区间内。
- **能力过宽、不写房间无害。** S2、S5 两种策略相当；冒烟中 S2 `rule` 偏低是小样本波动。
- **失败主体在报告环节。** `spark-x2.5-1.7b` 的状态口径为 86%–100%，通过率为 38%–78%；`spark-x2.5-4b` 在写入被拒后容易在报告前推理超时（P-D 的 S3 为 61 次）。

### 端到端测试

离线决策测试之后的第二项实验：按[委派闭环](#委派闭环)接入执行子 Agent，在 SimuHome 中执行，检验闭环本身，并把失败归到主 Agent、执行子 Agent 或 Runtime。

- 模型：主 Agent 使用 `deepseek-flash`；执行子 Agent 使用 `spark-x2.5-4b`，配置见[执行子 Agent 配置](#执行子-agent-配置)（维护人确认，2026-10-16）。`spark-x2.5-4b` 在正确范围下的失败较少，测得的问题主要来自主 Agent 与闭环；`spark-x2.5-1.7b` 留待闭环稳定后对照。
- 回复子 Agent 本轮不实现，以桩代替（维护人确认，2026-10-16），只判 `reply_to_user` 的结构化参数。
- 工具目录：24 档；跨领域用例另按 `domains` 开放天气工具，沿用[X1、X2](exposure-experiment.md#实施进展)的外部工具桩。
- 场景：复用执行子 Agent 实验的场景生成（房间、设备布置与初始状态）。主 Agent 的房间清单由场景给出房间标识，并按用例文件中的对照表附上中文名称；用户原话使用中文名称。
- 多轮：用例以脚本扮演用户。主 Agent 追问后，脚本按用例给出下一条用户消息（如选择候选中的一项，或“算了不用了”）；用例未准备回答而主 Agent 追问时，本轮结束，按用例的可接受集合判定。

用例覆盖以下类别，每例若干场景变体：

| 类别 | 来源 | 例句 | 期望 |
| --- | --- | --- | --- |
| E0 闲聊 | T0 | “今天好累啊” | 回应；不委派，设备状态不变 |
| E1 明确指令 | C1、C3、C4 | “打开客房的灯” | 委派一次；目标设备达到期望状态；以 `report` 汇报并引用任务。打开风扇时另设风扇的模式或风速不算越界写入：SimuHome 风扇接通电源后模式为 `off`、风速为 0（维护人确认，2026-10-16） |
| E2 批量 | C5 | “把全屋的灯都关掉” | 同上，`rooms` 为 `null`；列出全部房间与之等价（维护人确认，2026-10-16） |
| E3 能力不支持与目标不存在 | C6、C7 | “把客房的灯调到 50% 亮度” | 无写入；不重派同一目标。没有能达到同样效果的替代时（如开关灯调亮度），以 `report` 如实说明。目标房间有可替代的设备时（如无空调、有风扇），用户只说“打开空调”、目的不明，以 `clarify` 先问是否改用该替代，`options` 只含替代设备，不列出房间其他设备；未经确认写入替代设备、列出无关设备或只 `report` 均不通过。用户目的明确时（如“好热，开空调”）直接改用替代并汇报，现有用例未覆盖（维护人确认，2026-10-16） |
| E4 追问往返 | C8 | “开灯”，脚本回答选择其中一盏 | 转达追问，`options` 取自结果；续派以 `follows` 关联；只有所选设备变化 |
| E5 取消 | C8 | “开灯”，脚本回答“算了不用了” | 取消等待任务；无写入 |
| E6 隐含意图 | C3 场景 | “客房好黑” | 按推断委派；同 E1 |
| E7 多目标与例外 | C5 场景 | “关掉客厅和卧室的灯，厨房的别动” | 覆盖全部目标；被排除房间不变 |
| E8 上下文指代 | C3 场景 | “打开客房的灯”，汇报后“卧室的也打开” | 第二轮范围解析为卧室；两盏灯均为开 |
| E9 跨领域 | X1、X2 | “明天北京要下雨的话，把卧室的窗帘关上” | `domains` 含 `weather`；X1 关闭窗帘，X2 不写入。可一次委派（范围含房间与 `weather`），也可先委派查询天气（范围不限房间），读取结果后再委派关窗帘或直接汇报（维护人确认，2026-10-16） |
| E10 查询 | C1、C3 场景 | “客厅现在几度”“卧室的灯开着吗” | 委派一次，范围为所提房间；无写入；以 `report` 汇报；汇报内容与实际状态是否一致由人工核对（维护人确认，2026-10-16） |

判定：

| 层次 | 内容 | 方式 |
| --- | --- | --- |
| 设备状态 | 目标设备的期望状态、附带影响与越界，沿用执行子 Agent 实验的判定 | 程序，SimuHome 原生状态 |
| 每次决策 | 格式、决策类型、委派范围与引用，沿用离线决策测试的判定层次 | 程序 |
| 闭环 | 最终回复的 `kind` 与任务结果相符（`needs_clarification` 转为 `clarify`，其余为 `report`；P1 起 `respond` 与 `report` 由 Runtime 确定，见[回复类型与格式容错](#回复类型与格式容错)）、`refs` 覆盖本轮全部任务、未超过委派上限、无“未给出决策” | 程序 |
| 目标与追问 | `goal` 是否保留否定、条件与例外；追问是否针对缺失信息 | 人工抽查 |

失败归因按以下顺序判断：主 Agent 未给出决策或决策不符合可接受集合，归主 Agent；决策合格而设备状态或执行子 Agent 的报告不符，归执行子 Agent；任务状态、触发或结果整理与本节规定不符，归 Runtime。

同时记录每轮的耗时与 Token，按主 Agent 与执行子 Agent 分列，作为[时延与成本](#待确认)的实测依据之一；回复子 Agent 的耗时不在其中。

规模：首轮每类 10 个场景变体 × 3 次重复，约 300 轮（维护人确认，2026-10-16），结果不作统计结论；运行前报规模与 Token 估算，由维护人批准。

参照组（对应[意图理解评测讨论](https://github.com/hongyue0721/home_agent-experiments/issues/2)第 4 节 B 的分组）：

- **理想委派**：人工写出的任务直接交给执行子 Agent，即执行子 Agent 实验中的 C 类、X 类任务。C 类已有 P-D、24 档、`spark-x2.5-4b` 的数据（见[范围写错](#范围写错)的 S0 与[报告环节实验](executor-agent.md#报告环节实验)）；X 类只有 50、100、200 档的数据（见[实施进展](exposure-experiment.md#实施进展)），工具档位不同。E1–E3、E9 复用同一布置，以其通过率作为参照上限，端到端与之相差的部分归于主 Agent 与闭环。两者的变体与运行时段不同，只作参照，不作配对比较。
- **原话直达**：用户原话作为 `goal`，直接交给同一执行子 Agent（同一入口与配置），不经主 Agent，用于[分层是否值得](#需要主-agent-的实验)。该组只是实验基线，不表示产品允许绕过主 Agent。复用同一场景，不需要新的用例；适用 E1–E3、E6、E7、E9、E10，多轮用例（E4、E5、E8）与闲聊（E0）不适用。任务只补主 Agent 同样拥有的平台事实，不补对原话的理解（维护人确认，2026-10-16）：
  - `scope` 的 `rooms`、`device_types`、`capabilities` 为 `null`，`domains` 为会话开放的领域（E9 为 `weather`）。外部工具只按 `scope.domains` 开放，全为 `null` 时 E9 无从查询天气，测到的是工具未开放而不是理解。
  - `context` 只给房间标识与中文名称的对照，与主 Agent 输入中的房间清单相同。SimuHome 的房间只有英文标识，真实平台上房间名称本来可见。`constraints` 为 `null`。
  - 判定沿用设备状态与执行子 Agent 报告的检查（结构化结果、自洽、期望报告状态），没有决策与闭环两层；单轮用例中执行子 Agent 追问即与期望状态不符。E10 的汇报内容仍由人工核对。
  - 与主 Agent 组使用同一种子与变体，在同一批 SimuHome 实例上前后紧接运行，按变体与重复序号配对比较通过率、Token（原话直达只有执行子 Agent）与每条消息耗时。

#### 实施进展

2026-10-16 已实现会话入口、用例生成、判定与批量脚本，先用脚本模型在 SimuHome 上完成 E1、E4 各一个变体的冒烟，再运行三轮真实模型批次，见下文[批次结果](#批次结果)。闭环实现已合并到两个仓库的主干（`421d133`、`70d136b`）。

会话入口为代码仓库的 `python -m banju.session`，实现[委派闭环](#委派闭环)：

- 输入：`--session-file` 指向 JSON 对象，含 `rooms`、`domains` 与 `messages`（每项 `id`、`text`），格式同[触发与输入](#触发与输入)；`--system-prompt-file` 为主 Agent 系统提示。开始前核对会话房间清单与后端一致，不一致视为配置错误。
- 模型：主 Agent 与执行子 Agent 分别以 `--main-model-base-url`、`--main-model`、`--main-api-key-env` 与 `--executor-*` 指定；`--executor-api-key-env` 可给多个环境变量名，按任务执行顺序轮换。`--delegation-limit` 默认 3，即每轮委派上限。
- 输出：标准输出为一个 JSON 对象，含每轮的主 Agent 运行、执行记录、交付的回复桩、结束原因、耗时与 Token，以及全部任务记录。`--events-file` 另写运行事件，事件来源分为主 Agent、执行子 Agent 与 Runtime。
- 主 Agent 的输入在离线格式上增加：任务状态 `accepted`、`superseded`；会话记录项可带 `stub: true`；触发事件 `task_results`，`results` 为非空列表，每项含 `task_id` 与 `result`，校验同 `task_result`。
- 每轮的结束原因：`reply` 为正常回复，`no_decision` 为未给出决策；轮内异常分为 `infrastructure_error`（模拟器连接或超时、HTTP 5xx、响应不是有效 JSON 对象，按异常属性及其原因链识别）与 `runtime_error`（其余异常）。HTTP 4xx 与业务状态错误（如设备不存在）是正常的工具错误，照常返回给执行子 Agent。轮内异常保留错误详情并停止后续轮次，处于 `running` 的任务保持原状态，不补造结束状态。
- 退出码：全部轮次为 `reply` 时为 0，存在 `no_decision` 时为 1；启动阶段的配置错误与两类轮内异常为 2，顶层 `stop_reason` 分别为 `configuration_error`、`infrastructure_error`、`runtime_error`。
- 执行子 Agent 运行中工具调用遇到模拟器故障时，即使随后提交了结果，也按 `infrastructure_error` 结束，避免以 `completed` 掩盖基础设施故障。

用例、生成、判定与批量脚本在实验仓库 `agents/main_agent/`（`e2e_cases.json`、`e2e_generate.py`、`e2e_judge.py`、`e2e_batch.py`），运行方式见实验仓库 README。实现中的取舍：

- C7 原场景中的目标房间不存在，而端到端的房间清单来自场景，不能另造房间。E3 中来自 C7 的变体改为在已有房间请求打开空调，场景中无空调，期望仍为 `not_found`。
- E9 在用户消息前加“今天是某日。”，日期取自 X 用例的场景上下文，不含天气结果。
- E9 区分两种做法按首次委派的范围：`rooms` 为 `null` 且 `domains` 含 `weather` 视为查询，结果全部完成后允许再委派一次；范围含目标房间视为一次委派，之后只接受汇报。
- E10 问灯的变体按序号交替设置目标灯的初始电源状态，开、关两种答案都出现。
- 主 Agent 系统提示增加两处：触发事件可为 `task_results`；每轮最多委派 3 个任务，达到上限后须向用户汇报。
- 后续轮次依赖前一轮的执行结果。E4、E5 第二轮需要恰好一个 `waiting_user` 任务；若因第一轮执行子 Agent 的报告状态与期望不符或未提交结果而缺少该任务，第二轮的决策与闭环检查记为不适用，失败归执行子 Agent。主 Agent 第一轮未委派或未转达追问时，仍归主 Agent。
- 结果中有 `failed` 时，主 Agent 对每个失败任务重派一次是可接受的做法，范围不得超出该轮期望；同一原任务再次重派判为主 Agent 错误。首次执行的失败仍计入执行子 Agent 的检查，不因重派成功而抹去。
- 追问的 `options` 不逐字比对执行结果的候选：候选是执行子 Agent 写的自由文本，主 Agent 转达时可译为中文房间名；是否一一对应列为人工核对（维护人确认，2026-10-16）。
- `infrastructure_error` 与执行层的运行无效（如模型超时）记为无效运行，不计入统计；`runtime_error` 为有效失败，归 Runtime。

### 需要主 Agent 的实验

以下四项已确定进行（维护人确认，2026-10-15）：

| 实验 | 考察内容 | 前提 |
| --- | --- | --- |
| 子任务背景多少 | `context` 只给目标，与附带会话摘要相比，执行子 Agent 的通过率与成本差别 | 可用现有执行子 Agent 先做 |
| 失败处理 | 设备离线或拒绝执行时，主 Agent 重试、换用方式或告知用户，是否停止重派 | 仿真需支持设备故障注入 |
| 进行中修改 | 执行期间用户取消或改变要求时，未执行动作是否停止、已执行动作是否如实汇报；取消不是回滚 | Runtime 需支持执行期间接收新消息 |
| 隐含意图 | 用户不直说（如“客房好黑”“我要睡了”）时，主 Agent 是否按推断正确委派，以及不应执行时是否不做 | 主 Agent 实现；离线部分见[离线决策测试](#离线决策测试) |

以下为候选，待确认：

- **分层是否值得**：单个 Agent 直接处理，与主 Agent 加子 Agent 相比，通过率、成本与时延；单轮部分以[端到端测试](#端到端测试)的原话直达组进行；
- **是否委派与拆分**：闲聊、查询、多件事、带条件的请求，主 Agent 是否误派、漏派、拆分正确；
- **追问往返**：转达澄清后，用户以模拟回答补充，主 Agent 能否续派，是否替用户选择；首轮并入[端到端测试](#端到端测试)的 E4、E5；
- **汇报如实**：注入完成、部分完成、失败及虚报完成的子任务结果，回复子 Agent 的表述是否与平台状态一致；需先确定对自然语言回复的判定方式；
- **提醒提交结果**：执行子 Agent 以文本结束时由 Runtime 提醒一次提交结构化结果，与不提醒对照。已用执行子 Agent 单独测过：`spark-x2.5-1.7b` 在范围写错的 S1、S3 下通过率比不提醒高约 13–21 个百分点，提醒已与其他两项报告选项一起改为执行子 Agent 的默认行为，见[报告环节实验](executor-agent.md#报告环节实验)；经主 Agent 委派时的效果未测。
